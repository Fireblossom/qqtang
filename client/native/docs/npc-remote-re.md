# 默认NPC远端保持插值使用玩家速度表

2026-11-04。修正规则1/2/8 NPC接收端错误使用仲裁方速度表的问题；原版两端对同一档位使用不同表，这个差异不能按“理应一致”抹平。

## 调用链与数值

`0x005AFDFA` 为NPC创建远端控制器 `0x005D086B`，放在Actor+47C。`0x005D1348` 消费已解码的移动记录，把Speed低字节交给 **`0x005C450F`**，返回的float写到Actor+3B0。非仲裁方的 `0x005ABE96` 经 `0x005D09D6` 进入保持阶段 `0x005D13C2`，用该标量乘dt和0.04推进位置。

仲裁方 `0x005F3D0A` 则使用 **`0x005C452B`** 的NPC表。报文只传速度档，两种换算有差别：

| 档位 | 仲裁方NPC约px/s | 默认接收端约px/s |
| --- | ---: | ---: |
| 1 | 40 | 40 |
| 2 | 100 | 72 |
| 3 | 123.08 | 140 |
| 4 | 133.32 | 160 |
| 8 | 266.68 | 268 |
| 10 | 533.32 | 520 |

因此冰箱覆盖到2档后，默认接收端不是100px/s。原版后续记录会校正位置，不能将这张表的差异解释成各端位置应该永久分离；完整多记录时间调整仍有其他分支。

## 原生对照

```sh
.venv/bin/python tools/probe_npc_remote.py /path/to/client-patched
```

`npc_remote_v848.jsonl` 共793条：两张真实getter的13组数值（0～10及11/255上界钳制），加角色25/27/32×13档×四方向×1/17/20/25/100ms的780个保持单步。真实远端构造、`0x005D1348`、完整基础角色帧及远端保持推进函数执行，位置/标量逐float32位比较。补齐解码记录起点字段后重跑，793条与fixture完全一致。

输入是一条已经消费、无角点、终点较远的移动记录，队列没有下一条记录。图形为空，NPC分类/本地控制身份及简化世界是受控依赖；没有模拟完整收包/去重队列、延迟追赶、各角点容差、长期逐帧浮点累加或Windows整局。11/255是方法边界探针，不代表合法对局会自然发出这些速度档。

默认箱子NPC和命名Boss的接收插值改用已有 `battleengine.NativeSpeedScalarMilli` 的玩家表，保留原版10档上界钳制。仲裁方仍用NPC表，不更改永久速度、冰箱计时或移动报文的Speed字段。角色26本地一秒100px、接收端72px；角色27本地约123px、接收端140px的旧错误测试已按两张表修正。
