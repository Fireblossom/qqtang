# NPC共享发送历史、序列号与无固定心跳

2026-11-04，接续 `npc-remote-queue-re.md`。已撤下NPC每150ms固定心跳和每次发包递增的独立序列，改用原版NPC管理器的共享移动历史。

## 完整NPC循环的证据

`tools/probe_npc_publish.py` 执行真实NPC管理器构造 `0x005F3B59`，再运行整个 `0x005F3D0A` 多NPC循环。它在每个NPC后对同一个Manager+C调用 `0x005F34EE` 更新历史、调用 `0x005F3695` 取最后记录，循环末构造一份PLAYER_MOVE数组。

运动/碰撞、寻路反馈、Corner/End预测、有效速度输入、规则边界和外部编码/传输是明确的受控依赖；原版历史构造、共享序列、记录更新/裁剪、发送判断和逐条组包执行。传输入口捕获的是网络编码前的本机小端结构，没有把外部QQTPPP传输算进本轮原版对照。

共享历史最多保留8条。序列仅在没有历史、walk/方向/档位变化，或停止时整数位置改变时递增。行走中的Corner/End变化通常只改最后记录，沿用序列；当前位置和时间戳每次观察都更新，是否发出另由dirty决定。

同一终点下，新Corner只要有一轴为0，就不会替换已有Corner或触发dirty；终点变化时才可以顺带清空Corner。这项原版怪癖也保留。

玩家循环 `0x005F3810` 会调用 `0x005F3791` 累加150ms发送计时，NPC循环没有该调用。探针以20/40ms帧运行并跨过数秒场景时间，NPC历史计时始终为0：单个NPC的状态/预测不变时没有固定心跳。强制位置输入Actor+478则可额外触发发送，并在输出组合字节设置bit5。

两个NPC分别保持同样的walk/方向/档位，但终点不同，实际观察到两者每次循环都发送、共同沿用序列1；如果终点也相同，第二个NPC不会仅因ID不同而新建记录。这不是宿主自行推测的“每NPC各自历史”。不同NPC方向或档位交替时，序列会随全局遍历递增。

## 对照与宿主接入

```sh
.venv/bin/python tools/probe_npc_publish.py /path/to/client-patched
```

`npc_publish_v848.jsonl` 共32组、1215个世界帧，实际输出398条移动记录。覆盖四方向、1/2/3/10档、亚像素停止、Corner/End变化、速度/方向/walk变化、强制位置、低16位序列边界，以及2/3个NPC同/不同终点、方向、档位和停止状态。65534初始序列为明确设置的边界输入，不称为一次自然运行六万多次的证据。

Go从正式 `publishNPCMove` 逐角色回放相同输入，逐项比较输出NPC身份、序列、时间戳、Current/Corner/End、组合字节和速度；同时比较共享序列总数与历史长度。原版单批数组在宿主现有代理传输中仍按NPC身份分包，记录内容和顺序匹配，没有借此宣称UDP封装一字节不差。

`onlineMatch.npcMovement` 统一保存共享历史，规则8、Boss和探险均使用它；删除了各NPC独立的150ms心跳缓存。初次登记后的记录自然因空历史/状态改变发出，不额外伪造强制位置bit。普通玩家的发送计时不受这项修正影响。

侧车、引擎、协议相关全套通过；Mac正式构建和Windows/386交叉构建通过。累计NPC/共用模型基准7177条（7145+32），1215帧与398条输出均在这32组内，不重复加总。

原版世界NPC列表的所有增删顺序、控制权交接时整个世界生命周期、QQTPPP丢包/重传及源Win32整局仍需分别验证。此处输入由受控预测器提供，不据此重新证明几何或全部NPC AI正确。
