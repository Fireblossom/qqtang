# 商城收藏柜、材料整理、赠送与修理

更新：2026-11-03。原版 v848 静态反汇编与本机服务端核对。

## 收藏柜（已接入并联调）

脚本把控件叫 `UI.shop.recycler`，界面实际叫“收藏柜”，不是删除物品。道具箱右键物品→收藏→确认，调用 `ChangeItemStatus(uin, item, 2)`；收藏柜选择物品→取回，调用同一函数状态 0。

使用已有 `0x0085 ITEM_STATUS_CHANGE`。背包绝对更新为 `0x00D9`；服务端对收藏转换先发绝对更新再发成功回复。Client.exe 的成功回复路径会同步执行 `ui_updateMyItems()` 和 `ui_updateRecycler()`，原生宿主已补齐这两个回调；仅收到物品时更新缓存不足以保证两个窗口都刷新。

本地 58000，账号 1000007 的棉绒帽 19：收藏后 `GetDisableItemInfo` 返回状态 2，道具箱移除；取回后收藏柜数量 0，物品状态 0。两个转换被服务端接受，零 warn/error。窗口截图在 `/private/tmp/qqt-mall-re/collection-live`；发送收放用宿主调用，尚未逐一验收右键和确认框的鼠标路径。

## 材料整理（已接入）

`RequestSettleStorage`：Client.exe `0x0054C9B0` → XSection `+0x300` → QQTSection `0x1002F4B9` → `0x1002BD13`。**只改本地 500 格材料仓库数组，没有网络请求。**

先遍历，将 20001～22999 号道具移到前面；遇到非道具时，从尾部找最后一个道具换入。再从第一组末尾开始，以相同方式把 30001～31999 号材料聚到第二组；合成书留在最后。因此不能用稳定分组或按 ID 排序代替。实现和专项测试在 `props.settle_storage`。不改变主背包的顺序，也不改七格装备道具栏。

材料仓库查询同时过滤数量 0 和状态 2（收藏）的记录；数量 0 是服务端绝对更新保留的删除记录，不应继续画成可用材料。原版 UI 的“整理材料”按钮已实际点击验证，无新网络请求。

## 赠送（已接入，糖币）

调用链：Client.exe `0x0056B080` → QQTShop2ND 请求操作 2（`0x1000A3B2` → `0x1000B11F`）→ NetCenter 接口虚表 `0x1002F764` 的 `+0x114`（`0x1000EF01`）→ `0x1001CFD4`，传输命令 **0x025A**，请求 schema **0x040E**。

请求按大端编码：u32 UIN、u32 时间、u32 商品 ID、u16 交易类型 2、u16 支付类型、u32 收件 QQ、u8 附言长度、GBK 附言、u32 客户端版本、u16 混合支付。附言为紧凑变长字段，ClientVersion 紧随实际附言，而非最大数组末尾。长度为一字节，宿主截到最多 255 字节且不切断 GBK 字符，修正原包装函数 256 字节会绕回 0 的边界问题。

回复 schema **0x07F6**，固定 138 字节：u16 ResultID、128 字节 GBK ResultString、u16 DealType、u16 PayType、u32 PayMoney。**没有剩余余额字段**。余额通过现有 0x0094 NOTIFY_GAME_MONEY 发送绝对值，客户端不猜测扣款量。

本地服务端实现：

- 仅糖币。商品、单价、套装数量取服务端目录；赠送是替收件人购买新商品，**不转走发件人的背包物品**。永久装扮已拥有时拒绝，消耗品可叠加。
- `GiftInventoryItem` 在一个 SQLite 事务里扣款、收件人入包、保存附言；失败整笔回滚。应用层按 QQ 号稳定顺序锁住双方，避免相向赠送死锁。
- 新表 `player_gift_notices` 保存未投递的赠送记录。在线时推绝对物品数量和附言，离线时留待下次登录；成功写出 TCP 后才标记已投递，重复投递任务串行处理。
- 附言使用现有私聊通知展示，是**本地服务端的投递策略**，不声称这是原腾讯离线礼物邮件系统的复刻。商城没有聊天列表，因此在那里弹通知；大厅和房间显示在聊天区，对战中显示在游戏聊天区。
- 付款人余额在投递时重新读取，并串行发绝对值，避免并发赠送的旧通知覆盖新余额。

测试覆盖：紧凑 GBK 协议、事务回滚（在扣款/入包后故意让附言约束失败）、重复永久物品、余额不足、未知收件账号、并发不超支、相向赠送不死锁、离线附言与成功投递不重复、商城内附言和绝对余额。

本地 58000 实测（`/private/tmp/qqt-mall-re/gift-live`）：1000007 向 1000006 赠送两次商品 20050，每次是目录中一组 12 个医疗包、价格 1000 糖币。1000007 钱包 **99999999 → 99997999**，自身医疗包仍为 3；1000006 医疗包 **0 → 12 → 24**、钱包不变。在线附言在商城弹出，第二次收件人离线，重新登录后在大厅看到“离线礼物”。两条赠送、两次附言投递均被服务端接受，零 warn/error，客户端无异常。

本轮测试服为持久目录 `/Users/cduan/qqtang-test/qqt-server-present`，配置和测试账号库沿用原路径。

## 修理（协议已查清，结算未启用）

GetRepairPrice：Client.exe `0x0056B300` → 商城查询操作 1，以物品 ID 查目录 RESTORPRICE；QQTShop2ND `0x100022AA` 遍历商品表并返回结构 `+0xFC`。

RepairCommodity：Client.exe `0x0056B370` → QQTShop2ND 操作 3（`0x1000B1F4`）→ NetCenter `+0x124`（`0x1000F05C`）→ `0x1001D2A9`。原包装函数只写物品 ID，脚本传入的交易/支付类型未使用。

传输命令 **0x0263**，请求 schema **0x0430**，固定 16 字节：u32 UIN、时间、物品 ID、客户端版本。回复 schema **0x0818**，固定 136 字节：u16 ResultID、u32 ItemID、u16 AvailPeriod、128 字节 GBK ResultString。

本机发行目录 Commodity.ini 共 2978 个商品，RESTORPRICE 全为 0；本地目录也只发行永久商品。限时物品修理后如何恢复时长/耐久，尚无已确认规则。不能按购买另发一件物品代替修理，也不能对永久物品收取无意义费用。
