# 原生客户端开发的经验教训

记录做 `client/native` 过程中踩过的坑。每条写明当时发生了什么、原因是什么、以后该怎么做。原版行为的结论本身记在 `../README.md` 的"已确认的原版约定"里，这里只记做事方法上的教训。

## 一、最重要的几条

1. **界面引擎的行为不要猜，先查 gameUI.dll。** 按几个界面的截图推出来的绘制规则，换到新界面几乎都出了错：数字标签显示成 FFFFFFFF、价格折行错乱、分类标签不显示、每个界面左上角多一条白条、道具箱图标整体偏下。每一次都是读了原版的绘制函数（用项目技能 `qqt-binary-re`）才一次改对。新界面出现排版问题时，第一步就去找那个控件类型的绘制代码，不要先调参数凑效果。
2. **自动化测试绕过了界面，就会漏掉界面那一侧的状态。** `--call` 直接调脚本函数，跳过了登录按钮，脚本自己的 `uin` 一直是上一次的号码，结果商城报"无法连接商城服务器"。宿主要主动通知脚本（`NotifyMyUin`），而且至少要用真实点击路径再走一遍。
3. **先确认观察到的现象是真的，再排查。** 大厅聊天"发了不显示"查了半天，最后发现是截图裁错了位置。看截图用的 Read 工具按文件名缓存图片，同名文件重拍后看到的还是旧图，所以每次截图都要换新文件名。
4. **当仲裁方时，本地的每个裁定都要报给服务端。** 联网对战里大部分问题都是"本地做了决定，服务端不知道"。每局打完都要看服务端日志里有没有警告，日志是判断两边是否一致最可靠的依据。

## 二、反编译和转换

- **反编译器会悄悄输出错误数据。** uncompyle6 3.9.3 会把 5 个及以上常量组成的列表输出成常量表下标，例如角色名变成 `[12, 13, …]`。不报错、能运行，只是数据全错，影响了等级称号、表情、地图类型、角色列表和商城列表。以后改动转换工具或换版本时，要抽查几张数据表和原版是否一致，并对比改动前后的生成结果（旧结果可以先备份到 `/tmp`）。
- **先确认原版到底加载哪个文件。** 商城推荐页只有 1 件商品，原因是转换的是 `object/commodityCFG.pyc`，而 `uiMain` 用 `MyExecFile` 执行的是同名 `.py` 源码；`.pyc` 是 2007 年的旧编译结果，记录的源文件时间对不上，Python 2.3 会忽略它。遇到数据不对时，先查脚本里的加载路径，再看 `.pyc` 头部记录的源文件时间。
- **Python 2 的语义会直接影响排版。** 除法（`/` 对整数向下取整）、`sort(cmp)`、以及 `len()` 返回 GBK 字节数，脚本拿它算文字宽度（如 `len(name) * 6`）。宽度、位置算出来不对时，先想是不是 Python 2 和 Python 3 的差别。
- **运行宿主会改写客户端目录。** 原版脚本每次启动都会重写 `devConfig.txt`，会把 CRLF 换成 LF。在别人的客户端目录里测试前要先备份。

## 三、界面引擎（宿主）

- **绘制规则要按原版的数据来源算。** 道具箱图标偏下，是因为居中时用错了尺寸，竖直方向也没有居中。原版按 DIMG 整张画布的尺寸居中，再加帧偏移；我们按单帧尺寸算，而且只做了水平居中。类似的还有 NUMLABEL：字形格子大小取 `textwidth × textheight`，不是把条图宽度均分。改之前先弄清原版用的是哪个尺寸。
- **修一处绘制规则后，要把用到它的控件都过一遍。** 改 `bkImgFlag` 前，列出了 48 处用法，逐个看 rect 和底图尺寸，提前知道大厅玩家列表的底图会上移 6 像素，不会误以为改坏了。
- **命中检测按原版规则做。** 禁用的控件曾经把点击吃掉（房间队伍颜色按钮点不了）。原版规则是：禁用或隐藏的控件连同子控件都跳过，点击继续交给下面的兄弟控件；任何可见、启用、非 Static 的控件都会接住点击，不需要有 `OnClick`。
- **调用脚本函数前先看它画的是哪个控件。** 大厅列表收到新玩家后调用的是 `updatePlayer`，它画的是引导栏里的列表；大厅右侧的列表是 `updatePlayer2`，只在 `OnInit` 时画过一次，所以别的玩家一直不出现。原版调用的是两个都画的 `ui_NotifyPlayerUpdate`。
- **宿主弹系统对话框时要让脚本换按钮。** 原版显示对话框后执行 `ui_msgBox(类型)`，没调用时按钮还是上一次的图片（只有一个按钮却显示“同意”）。
- **不要把 Tab 停靠序号当作输入转发对象。** gameUI 的 `+0x110` 保存最近焦点子控件的 groupstop 序号，`0x1002745C` 用它找下一 Tab 停靠项；不是文本输入指针。加好友脚本确实在聚焦输入框后又用 `ui_setCapture` 聚焦父对话框，覆盖了编辑焦点。本机按修明显 bug 的既定约定保留已选定输入框，捕获仍归对话框；这是行为修正，不是补出一个原版不存在的子控件字符转发。证据和验证见 `ui-keyboard-re.md`。
- **宿主生成的回调要遵守脚本自己的约定。** 宿主弹的提示框用句柄 -1，而脚本的 `ui_OnMsgBoxResult` 把 -1 当成"执行 execStr"，点确定时报错。改成 0 之后不会命中任何分支。宿主要调用脚本回调时，先读一遍脚本里处理这个回调的所有分支。
- **用别的字体模拟宋体时，要按宋体的格子宽度排版。** 系统字体比宋体宽，按系统字体量宽度会导致折行位置和原版不一样。现在按宋体格子宽度折行，画的时候再把整行压到宋体宽度。原版的效果本来就不完美（4 位数价格会被截成"1000 糖"），照原样实现，不要自作主张"修好"它。
- **覆盖率工具按固定的文件列表统计。** 新增模块（`chat.py`、`shop.py`）后，要把它加进 `tools/native_coverage.py` 的列表，不然统计的数字不会变。

## 四、协议和服务端

- **只看消息格式不够，要读服务端处理的完整流程。** 建房成功只返回房间号，客户端还要接着发进房请求，才能拿到完整的房间信息。这一点只有读服务端代码才知道。
- **Go 的字段名可能和实际含义对不上。** 购买回包最后一个字段叫 `TicketLeft`，服务端实际填的是剩余糖币。按字段名理解之前，先看服务端往里写的是什么。
- **单元测试要照着 Go 编码函数里的偏移来写，不要凭印象。** 写物品结构测试时把字段顺序记错了（实际是 2 字节物品编号在前，4 字节数量在后），测试失败才发现。好在错的是测试，不是客户端。
- **联网对战里出现过的"两边不一致"：**
  - 爆炸消息没带被炸掉的墙。墙被炸掉的事件是 `EventCellDestroyed`（500 毫秒后才移除），不是 `EventCellDamaged`，两种都要带上。
  - 本地引擎替 AI 捡了道具，却没通知服务端。
  - 本地引擎自己判定 AI 被困，服务端那边没有。原版是每个客户端只判自己被困，所以给引擎加了只判本地玩家的选项。
  - 拾取记录按"道具 + 格子"记，同一格会重新出现道具（小鸟掉落、阵亡掉落），旧记录要清掉。
  - 空格可能刚好按在引擎两次推进之间（引擎每 20 毫秒推进一次），泡放不出去。按键要留到下一次推进时再用。
- **开局被拒时，先按错误码查服务端。** 一个人对 AI 开局被拒（0xF004），原因是房主背包里要有 AI 卡（物品 30099）。测试数据用本地 GM 接口（`127.0.0.1:18100/gm/api`）准备，只动本地测试库，并告诉用户改了什么。
- **未处理的消息要打日志。** 每次进大厅都有一条未处理的 0x00A2，查出是好友列表。有日志才知道还缺什么。
- **先查原版会不会处理这条消息，再决定怎么处理。** 服务端用 0xA6 通知“对方同意/拒绝”，但原版 `QQTSection` 的分发只把 0xA2～0xA5 交给好友模块，0xA6 根本不处理；原版是靠关联请求的 0xA3 回包显示结果的。宿主把 0xA6 映射到原版对应的提示文字，并在汇报里说明这是适配服务端，不是原版行为。区分“回包”和“推送”可以看内层序号：服务端推送时清零，回包沿用请求的序号。
- **数据的归属要读持久化代码。** 好友关系是单向的（`friendships` 表按 owner 存），同意申请只改申请人的名单。脚本里“同时添加对方为好友”默认勾选、同意时发反向申请，正是为了这一点。只看协议会以为同意后双方都成了好友。
- **服务端生成的数据可能和原版不同，但客户端要照实显示。** `Commodity.ini` 全部写 `AVAILPERIOD = 0`，确认框就显示"使用时间: 0 天"，这是服务端数据的问题，不在客户端里掩盖。

- **每一步都要确认服务端真的接受了。** 第一次测"道具场"时，客户端以为已经切成道具场，对局也照常开始了，看起来测试通过。其实服务端拒绝了换地图请求（211 不是道具场地图，日志里只有一条 warn），又因为客户端没发"改房间类型"请求，仍然按无道具场开局。之后每个测试步骤都要去服务端日志里找对应的成功记录（例如 `qqt_room_type_changed_1`），再看有没有 warn。
- **服务端的业务规则会挡住测试路径。** 一个人在道具场不能补 AI（AI 补位只用于无道具场），所以测带入道具必须开两个客户端。遇到开局被拒时，按错误码在 `match_start_dispatch.go` 的 `classifyStartGameRejection` 里查原因。

- **服务端已有的同类实现是最好的参考。** 做非仲裁方时，服务端 AI 运行时（`competitive_ai_runtime.go`）就是一个现成的"非仲裁方"：引擎打开 `NativeOutcomeAuthority`，把请求事件转成网络消息，等仲裁方确认。照它做，引擎只需要加一个选项（`NativeRequestPlayerID`），不用另写一套逻辑。
- **双客户端联调要分清是不是自己造成的提前结束。** 自动化的走位很粗糙，两次联调都是有人把自己炸死，对局十几秒就结束了，拾取之类的路径根本没走到。这种路径要用单元测试补上，不能因为"联调通过"就当作覆盖了。

## 五、资源和画面

- **合成图片时要考虑所有素材组合。** 阵亡动画有一帧超出 100×100 画布，合成时数组越界，客户端在对战中崩溃。修复后把所有角色、队伍颜色、动作和帧都合成了一遍确认。
- **伪 C 丢掉的 `this` 会让人读错。** 包子店的两排小包子，伪 C 里只看到绘制函数用同一个坐标，就记成了"两排起点相同"；实际上建店函数末尾用 `0x005C47DC` 给两个图像对象设了不同的基准点，伪 C 把调用对象（`mov ecx, [esi+0x3c]`）丢了。看到 `FUN_xxx(常量, 常量)` 这种没有对象的调用，要用 `pe dis` 看前面的 `mov ecx` 是谁。
- **画面位置拿不准时，用当年的对局录像核对。** B 站有不少停服前的原版录像（搜"QQ堂 抢包子"）。做法：`api.bilibili.com/x/web-interface/search/type` 搜视频，`x/player/pagelist` 取 cid，`x/player/playurl`（`fnval=16`）取视频流；海外访问主节点（akamai）几乎下不动，备用节点要带完整浏览器 UA、Referer、Origin，并且必须用分段请求（`-r`，每段 2 MB），否则被拦（567）。用临时环境里的 OpenCV 截帧，把 640×480 的画面放大到 800×600，用带透明蒙版的模板匹配（`TM_CCORR_NORMED`）找素材位置；先拿几个地图元素校准整段录屏的偏移（这段是 (−2, −6)）。这样查出了店里包子数的位置，也发现场景道具一直画低了 15 像素。
- **Go 的 `[]byte` 转成 JSON 是 base64 字符串。** 雕像的碎片列表用 `[]byte` 输出，客户端拿到的是字符串，雕像一完成就崩溃。要给客户端的数字列表用 `[]int`。
- **查服务端日志先列出所有事件名再搜。** 有一次以为"没人用过黑泡"，其实道具使用的记录名是 `world_item`，我搜的是 `use_item`。先用 `grep -o 'result":"qqt_[a-z_]*'` 列出这一局全部的事件名，再判断有没有。
- **用多个子任务并行逆向一个新玩法很有效。** 雕像分成"雕像"、"碎片"、"48 号道具"三路同时查，各自交回一份带地址的规格，主线照着写代码。给子任务的问题要具体到函数地址和要回答的几件事，并要求它们只查不改。
- **改了规则辅助进程，联调前一定要重新编译（`tools/build-sidecar.sh`）。** `go test` 不会更新客户端用的那个程序。有一次离开处理"没生效"，查了半天才发现跑的是旧程序。
- **半透明、会动的特效很难在录像里做模板匹配。** 泡泡罩叠加在移动的人物上，匹配误差大到没法用。这种情况以代码为准，录像只用来比外观（亮度、大小）；正是比外观发现了混合方式不对。
- **用户说"不对"时先核实看到的是什么。** 用户说"地上的包子太小"，其实那是店里的包子数图标：店没画出来，计数图标露在草地上。先找出画面上那个东西是谁画的，再改。
- **逆向找不到素材时，把候选素材排成总览图，用眼睛找。** 被困泡泡的图片编号在 Client.exe 里是运行时算出来的（对象编号为 `类型 << 24 | 编号 << 8 | 动作`），搜不到常量。最后把所有 misc 图的第一帧排成一张总览图，才找到糖浆团（misc111），顺带找到了结算画面的素材。这种靠推断得到的结论要标明"推断"。

## 六、工具和环境

- **沙箱限制：** 客户端会写 `~/Library/Application Support/QQTangNative/state.json`，运行客户端要申请完整权限，否则会报 PermissionError。
- **自动审批：** `cd …; tools/prepare-ui.sh` 会被拒（脚本里有 `rm -rf`），改用绝对路径并用 `&&` 连接就能通过。
- **客户端参数：** `--shot 路径@毫秒` 可以在运行中途截图，可以写多次；`--screenshot` 是退出时的最后一帧。抢包子 1 对 1 每边只有 1 个包子，开局几秒就可能分出胜负，截图要排在开局后的几秒内。
- **临时目录：** Go 工具链在 `/tmp/qqt-go`、测试服务端在 `/tmp/qqt-out`，重启后都会消失。macOS 上覆盖正在运行的程序可能让它崩溃，所以要等对局结束再重新编译规则辅助进程。
- **测试服务端：** 服务端进程曾经无声无息地退出过。测试前先用 `lsof` 看 18000、18001、18080、18100 端口有没有在监听。
- **反汇编工具：**
  - `pe func` 遇到第一个 `ret` 就停。像"图片没加载就返回 10"这种提前返回会把函数截短，要改用 `pe dis` 多读一些。
  - `cdq; sub eax, edx; sar eax, 1` 是 C 的有符号除以 2，结果向零取整，和 Python 的 `//` 不同。移植时用 `int(a / 2)`。
- **反汇编工具（续）：**
  - `pe dis` 的起始地址落在指令中间时会直接输出空，要换几个起点试（往前挪 0x10 左右）。
  - 原版的业务逻辑大多在 DLL 里，通过类似 COM 的服务注册表取接口：`[0x7FAF04]` 的虚表 `+0x14` 按 GUID 取服务。追实现的方法是：在所有 DLL 里搜这个 GUID 的 16 个字节，找到用注册表 `+0x20`（GUID、类 ID）注册它的地方（QQTModules.dll），再搜类 ID，找到注册这个类的 DLL（QQTSection.dll），最后在那个 DLL 里扫描构造函数写入的大虚表。
  - Core.dll（`.tvm0` 段）和 Client.exe 的部分函数加了虚拟机保护，静态读不了。不要试图还原虚拟机代码（公开的去虚拟化工具只支持 64 位的新版腾讯壳），而是用 `tools/probe_vm.py` 在 Unicorn 里把它当黑盒跑：给一个按偏移布置好的假角色对象，记录它写了哪些字段、调用了哪些普通函数，再用静态分析读那些普通函数。复活状态（`0x00881FE5`）就是这样查清的。函数要读的对象（状态机、子对象）缺了就会跑偏，报错时按报错地址补上对应的假对象，碰到加载图片、特效的代码就预先填一个假指针跳过。
  - 三个程序里都搜不到某个原生函数名（例如 `ChangePosition`），说明原版根本没注册它，脚本在原版里调用它也会出错。这种函数不要实现。
- **zsh 不会自动拆分变量**，`set -- $a` 拿不到多个参数。要拼请求参数时，直接用 Python 发请求。
- **同一批并行执行的工具调用看不到彼此的结果。** 修改文件和运行检查放在同一批里，检查读到的是改之前的文件（覆盖率数字没变）。有依赖的步骤要分开执行。
- **两个客户端联调：** 一个放后台先登录，另一个晚几秒启动，按各自的时间轴安排点击；两边各写日志，靠日志里的 `[friend]` 行核对先后顺序。只有一次截图机会时，要看中间状态就分成几次运行，每次截图换新文件名。
- **长时间的测试放后台跑，汇报前一定要回来看结果。** 联网对战一局要 1～2 分钟，可以放后台，同时做别的；但汇报"都通过了"之前要确认它真的跑完、真的通过。

## 七、协作

- **长任务的子代理要分步提交。** 多真人同局的子代理两次中途停止，第一次停下时所有改动都没提交。给子代理的任务说明里要写明"每完成一步就提交"，停下后主会话才能从它的提交接手。
- **多个会话同时改同一批文件会互相覆盖。** 曾经两个会话同时写房间功能，`room.py` 被覆盖，客户端启动不了。大改之前先看文件修改时间，确认没有别的会话在动。我还把自己的修改误报成"别的会话还在写"，所以汇报之前要先核实。
- **改了服务端共用的代码要单独说明。** 给 `internal/game/battleengine` 加的两处改动都是默认关闭的选项或只读函数，补了测试，并请用户单独过目。
- **用户没选方案时，按建议的方案做，并明确说出来。** 用户只说"继续"时，按自己推荐的方案往下做，在汇报里写明选了哪个、为什么。
- **用户已同意（2026-10-30）：用 Unicorn 黑盒运行 Client.exe 里受虚拟机保护的函数。** 静态读不懂的保护代码，用 `tools/probe_vm.py` 在本机模拟执行，看它改了哪些字段、调用了哪些普通函数，不去破解或还原虚拟机本身。只读原版文件，结果写到 `/tmp` 或 `generated/`，不提交。这样查到的结论注明"Unicorn 黑盒运行"和函数地址；黑盒里伪造的对象可能不完整，只覆盖跑到的分支，没跑到的分支仍按推断处理。
- **不提交代码，不提交生成的脚本。** `generated/` 里是腾讯的代码，已在 `.gitignore` 里。装 Ghidra 之类的工具前先问用户；用户已经说过先不装 Wine。

- **特殊规则的消息名不能代替原版语义。** 机器的Free/Angry/Grace/Cool实际是发射模式，0x115D发的是延迟泡批次；模式包count字节高四位还有机器索引。机器普通放泡则是0x1159投泡，旧服务端误限为规则2/8。先追原版生产/接收函数，再决定状态和传输边界。
- **测试机器人也要遵守方向通行位。** 机器门就绪只开横向通行，BFS只看Open会把垂直穿门当成捷径，机器人会卡在门下。修复时同时检查源格出口和目标格入口，并用真实长局验证反复启动。
- **Ready不等于所有子对象停止计时。** 机器充能对象从构造时0发开始，Ready期仍更新，3000ms时通常已有1发；消费不重置补充计时。用Unicorn测构造、更新和消费边界，比按“冷却”一词猜计时方式可靠。

- **先看完整组件表，再沿用普通输入。** 箱子规则不注册普通放泡，Space推箱，49道具才造泡；发射器实际先发1167，再本地造隐藏泡和侧挡，并不是旧调研猜的1159飞泡。原版整数常量必须核对十进制，例如0x3724是14116。
- **原始出生池可能包含重复槽位。** 箱子1404重复(10,2)，通用验证曾挡住建局；规则8按原版槽位采样保留顺序/权重，不能为了通过验证去重并改变SpawnSeed结果。
- **已有记账fallback先验证再改。** 箱撞1162后独立0FA7已经能按服务端fallback扣一层；若又把1162当10F4记账，会重复扣层。火箱LossHP=500对玩家仍是一层，NPC与玩家的退役路径也应分开验证。

- **新叠加层先检查引擎的全局假设。** Boss 局 GAME_BEGIN 把所有人投影成 1 队，而引擎建局要求至少两队；不先写单测，真实开局会直接在 sidecar 初始化失败。类似地，单队时引擎自己的"只剩一队就结束"必须交给服务端（`ExternalConclusion`）。
- **同一个原版函数的参数含义只查一次、到处共用。** `0x005D9BBF(…, 400, 0)` 的 400 在踢炸弹里已经核对是 400 px/s，Boss 逆向文档推断成 400 ms；以仓库里已核对的结论为准，再回头修正文档。
- **测试机器人要会打新目标。** 自动客户端只把玩家当目标时，Boss 局跑一整局都碰不到 Boss，受伤、掉落、死亡路径完全没被覆盖；给机器人加上"Boss 在炸程内"后才在实局里验证到。
- **看到"开局失败"先分清是哪一端。** 701 的 Boss 局服务端已正常开局并扣了召唤道具，失败的是客户端 sidecar 建引擎（单队无法走分队出生）；先查服务端日志的 game_begin，再决定改哪边。
- **先从 Client.exe 的入口顺着 DLL 分发查到底，再移植处理函数。** QQTSection 里有完整的好友追踪（`CFriendHandler::RequestPursuit` `0x1000F7BF`、回复处理 `0x10010D83`），但这个版本的 `XSection::DoFriendTask`（`0x1002C68D`）对任务 3 只提示"抱歉，好友追踪已关闭!"。先写了追踪、实测也通了，才发现原版根本不走这条路。
- **原版的测试地图要先看元素会不会被围住。** 115 的传送门四周全是坚石、414 的光环被箱子包住，自动客户端跑一整局都碰不到；先查地图层，换没被围住的图（820 的传送门）或让机器人先去打这些元素（117 的爆炸石）。
- **按键读取可能藏在专用getter里。** Tab不是直接调用“读第22键”，而是 `0x005A4C2B` 读键盘对象 `+0x22 = +0xC+22`，调用者组件也确实注册在规则中。不能因没找到显式22参数就断言没有输入路径。这里还要继续核对页偏移是否用于实际索引：原版只改边界检查，getter漏加偏移，已按既定约定修正。
- **选择谓词不一定包含真正使用许可。** 原版Ctrl的VM谓词只看状态与持有，准备Prop的冷却/模式/拒用在选中后检查，失败并不继续扫描。此前在Ctrl循环里加入冷却跳过改变了原版行为；已用原生选择器和PickedUpState分别实跑纠正。输入锁又在键盘层，只屏蔽道具键，Tab仍可用。
- **先确认图片对象是否被重建，再决定保留还是重置相位。** 机器发射只切动作，保留相位；雕像每次存放/拆除会销毁并重建阶段图，从0开始。二者同用300ms默认周期，也不能共享全局时间选帧。完成英雄本身也可能有多帧（misc242为2帧），不能因其他英雄只有1帧就一律固定第0帧。
- **不要把显示格数当作库存容量。** 原版物品管理器是可增长向量，七格是窗口，数量是包装的32位值。直接执行通用发放/扣除后，12种物品和256个的堆叠都能保留，用尽后还会紧凑前移。原生客户端启用完整库存，训练观察仍保留原有七格契约，见 `item-slots-re.md`。
- **保护代码的调用方不能代替完整初始化路径。** 准备道具顺序实际由普通代码 `0x005B974A` 读取Section接口的房间栏，再进入VM发放。角色探针曾卡在TerSafe数值包装和图形初始化；隔离这些外部依赖后，原版构造/初始化与槽位回调可完整运行。可复现工具为 `tools/probe_item_slots.py`。
- **动画默认周期和调用者时间单位一起核对。** 机器图片默认300ms；世界同一dt既增加场景时间也原样传给地图层，元件只在发射图上乘3。各图片在隐藏时暂停并保留相位，不能用全局时钟模帧数替代。原版还使用上一帧状态更新、新状态绘制，800ms边界会先显示冷却图、下一帧才恢复其计时；原生函数基准见 `machine-animation-re.md`。
