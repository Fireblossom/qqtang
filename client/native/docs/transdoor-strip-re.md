# 传送门（CMETransDoor）与传送带（CMETransStrip）逆向记录

来源：`~/qqtang-re/decompiled/Client.exe/decompiled.c`（Ghidra 伪 C），关键处用 capstone 反汇编核对；数据取自 `client-patched` 下的 `Client.exe`、`object/mapElem/mapElem.py`、`map/*.map`、`effect/TransDoor*.eff`、`QQTMsgData.bin`。

标记：**[证实]** 代码或数据里直接读到；**[推断]** 由代码推出、没有运行验证；**[未知]** 没查清。

## 0. 公共背景

### 0.1 地图元素对象（基类 `CMapElem`，虚表 `0x007A369C`）

| 偏移 | 含义 | 依据 |
| --- | --- | --- |
| `+0x04` | 元素 ID | 构造 `0x005EEC60` [证实] |
| `+0x08` | 行 row（short） | `0x005EF073` 由 `(row, col)` 写入；`0x005EECAF` 用它乘地图宽度 [证实] |
| `+0x0A` | 列 col（short） | 同上；画图 x 用 `+0x0A*40` [证实] |
| `+0x0C` | 状态：1 正常、2 正在被炸毁（500 ms）、3 移动中 | `0x005EF283`、`0x005EF2CF`、`0x005EF0BE` [证实] |
| `+0x14` | 元素属性（mapElem.py 解析结果）：`+0x0C` LifeTime，`+0x14` 标志位，`+0x18` GridAttr 数组 | `0x005EF264`、`0x005EF272`、`0x005EF1AA` [证实] |
| `+0x1C` | 所在层管理器 | `0x005EEE48` [证实] |
| `+0x20` | 正常状态播放的特效 | `0x005EF283`、`0x005EF003` [证实] |

虚表槽位：`+0x04` 初始化，`+0x0C` 绘制（`0x005EF003`），`+0x1C` 每帧更新（基类 `0x005EEE71`），`+0x2C` 玩家能否进入（`0x005EF1AA`），`+0x30` 火焰能否穿过（`0x005EF20F`），`+0x34` 可否炸毁（`LifeTime >= 0`），`+0x48` 事件处理（基类 `0x005EF322`）。

### 0.2 层管理器（构造 `0x005D7EC5`，虚表 `0x007A3444`）

- 每张地图有 3 个层管理器，在游戏对象（`+0x1310` 处的逻辑对象，下称 G）的 `G+0xE2C`、`G+0xE78`、`G+0xEC4`；从外层看是 `+0x213C`、`+0x2188`、`+0x21D4`（`0x005FD788`、`0x0060D31B`）[证实]。`G+0xE78` 是中间的"元素层"（`other-rules.md` 已记，`0x005EEE48` 用它判断）。
- 字段：`+0x04` 列数 15，`+0x18` 行数 13，`+0x2C` 元素 ID 网格，`+0x30` 元素对象网格，`+0x34` = G，`+0x3C..+0x40` **传送门配对表**（每项 8 字节 `{门对象, 目标门对象}`），`+0x48` 洗牌计时器，初值 **3000 ms**（`0x005D7EC5`）[证实]。
- 每帧 `0x005D8A77(dt)`：先按**行外层、列内层**遍历网格，对有元素的格子调用元素 `vt+0x1C(dt)`；然后处理洗牌计时器（见 1.3）[证实]。
- `0x005D865C(row, col)` 取格子里的元素；`0x005D8BC1(row, col, dir)` 判断能否进入，格子空时返回真，越界返回假，否则调用元素 `vt+0x2C` [证实]。
- `0x005D8D93(事件, 参数, row, col)`：事件 0xD 洗牌；其余事件转给 `(row, col)` 元素的 `vt+0x48(事件, 参数)` [证实]。

### 0.3 角色对象（虚表 `0x007A1D2C`，构造在 `0x005AFCE6` 附近）

| 偏移 | 含义 |
| --- | --- |
| `+0x328` | PlayerID（u16） |
| `+0x338` / `+0x33C` | 当前 x / y（float，像素，是角色中心；格子中心为 `col*40+20, row*40+20`） |
| `+0x3A8` / `+0x3AC` | 上一次的 x / y |
| `+0x34C` | 角色的位置挂点子对象（特效挂在这里，跟着角色走） |
| `+0x3B4` | 朝向：0 右（col+1）、1 上（row−1）、2 左（col−1）、3 下（row+1）（`0x0060D37C` 的分支）[证实] |
| `+0x3B8` | 移动标志：2 = 正在走（开始走时置 2，`0x005AC982` 附近），1 = 站立 [证实] |

- `0x005AD322(x, y)`（thiscall，ECX = 角色）：先把当前位置存到 `+0x3A8/+0x3AC`，再写入新位置，并刷新挂件位置。它本身不发网络消息 [证实]。
- 角色 `vt+0x88` = `0x005AB203`：若是本机控制的角色，调用 `0x005A544A`：把 4 个方向键从按键栈里弹出，并把消息层 `+0x7C4`（输入开关）清 0，即**锁住输入** [证实]。
- 角色 `vt+0x8C` = `0x005AB233`：若是本机控制的角色，消息层 `+0x7C4 = 1`，即**解锁输入** [证实]。
- `0x00534990(id)`（跳板 `0x00404CC3`）：id 等于本机玩家（`+0x3820`/`+0x3822`），或在某个本机代管名单里时为真。下文称"本机控制"。名单很可能是仲裁方代管的 AI [推断]。
- `0x005A287F(id)`：按 PlayerID 找角色对象 [证实]。

### 0.4 角色与地图元素的事件从哪里来

`0x005C87B0`（每帧游戏更新）在开局 3000 ms 后调用 `0x005F43B1(角色)`，处理**本机玩家**，以及仲裁方代管的每个角色（`0x005C8BB9(i)`，只有本机是仲裁方时，`+0x4B34 == +0x4B40`）。远端玩家不处理 [证实]。

`0x005F43B1` 调用"通用检查"列表里的每个对象（`0x005F4350` 按类型 1 放进 `+0x08` 列表）。其中 `0x0060D2CD`（虚表 `0x007A4598`）负责地图元素，依次做三件事（三层各做一次）[证实]：

1. `row = (int)y / 40`、`col = (int)x / 40`，用 `+0x3A8/+0x3AC` 算出上一格。
2. 若格子变了，并且 `+0x3B8 == 2`（角色在走）：给新格子的元素发**事件 4**（进入格子）。
3. 若格子没变，并且 `+0x3B8 == 2`：如果朝向的相邻格三层中有一层不可进入，就给相邻格的元素发**事件 7**（顶住，例如推箱子）。
4. 无论如何都给当前格的元素发**事件 6**（站在格子上），每帧一次，不看角色状态。

所以：**进门只看角色中心所在的格子，并且必须是自己走进去的**。被传送带推进门格时 `+0x3B8` 不是 2，不会触发 [证实条件；实际效果为推断]。

### 0.5 GridAttr（mapElem.py 里的 `GridAttr`）

`0x005EF1AA`（玩家进入）的方向掩码：方向 0（右）→ `0x8`，1（上）→ `0x4`，2（左）→ `0x2`，3（下）→ `0x1`，4 → `0xF`（带 `0x80` 的是反方向）。`0x005EF20F`（火焰）：方向 0 → `0x800`，1 → `0x400`，2 → `0x200`，3 → `0x100`，4 → `0xF00`。位为 1 表示可以通过 [证实]。

传送门（17026、17029）和传送带（17121–17128、17130–17133）都是 `GridAttr = (3855,)` = `0x0F0F`：玩家四个方向都能通过，火焰四个方向都能穿过，不遮挡角色（`0x00F0` 这几位为 0，mapElem.py 注释说中间两个半字节是"遮蔽玩家/遮蔽火焰"）[证实数值；位含义来自上面两个函数和 mapElem.py 注释]。

两者都没写 `LifeTime`，默认值 −1，不可炸毁 [证实]。

## 1. 传送门 CMETransDoor

- 注册：`0x00613C20`，`FUN_005F528A("CMETransDoor", 0x4C, …)`；元素 ID 17026、17029 都映射到这个类（表 `0x007A3848`）[证实]。
- 虚表 `0x007A4B14`：`+0x04` 初始化 `0x00613D4E`，`+0x1C` 更新 `0x00613D6E`，`+0x48` 事件 `0x00613E4D`，其余用基类 [证实]。
- 字段：`+0x38` 已登记（byte），`+0x3C..+0x48` 待处理表（std::vector，每项 16 字节）[证实]。

待处理表项（`0x00613E4D` 组装，`0x00615596` 追加，`0x006155A7` 删除）[证实]：

```
+0  u16 PlayerID
+4  i32 剩余时间（ms），初值 2000
+8  i32 类型：8 = 正在进入（入口门），9 = 正在出来（出口门）
+12 ptr 挂在角色身上的特效
```

### 1.1 两个 ID 有没有区别

没有。代码里不看元素 ID，配对也和 ID 无关。区别只在 mapElem.py 的偏移：17026 `offset=(6,7)`，17029 `offset=(5,7)`；两张图 `object/mapElem/common/elem26_stand.img`、`elem29_stand.img` 都是 4 帧 52×52 [证实]。

### 1.2 登记

门第一次更新时（`0x00613D6E`，`+0x38 == 0`）调用层管理器 `0x005D8E20(0xB, 门)`，在配对表末尾追加 `{门, 0}` [证实]。层管理器按行外层、列内层更新元素，所以**配对表的顺序就是门在该层的行优先顺序** [证实]。门析构时发事件 0xC（`0x00613CFB` → `0x005D8E20`）：删除自己那一项，并把指向自己的目标清 0 [证实]。

### 1.3 配对：仲裁方定期随机洗牌

- 每帧 `0x005D8A77`：`+0x48 -= dt`，减到 ≤0 时重置为 **30000**。如果本机是仲裁方（`G+0x3824 == G+0x3830`），并且配对表不空，就取一次 `rand()`，广播 0x1176 子类型 0xD，并在本地洗牌（`0x005D8D93(0xD)`）[证实]。
- 所以第一次洗牌在开局后约 3000 ms，以后每 30 s 一次。第一次洗牌之前所有门的目标都是 0 [证实]。
- 洗牌 `0x005D927B(seed)`（反汇编核对，伪 C 丢了分支）[证实]：

```python
def lcg_rand(seed):  # 0x004522F0（跳板 0x0040F722），全部按 uint32 运算
    s = seed
    s = s * 0x41C64E6D + 0x3039; a = (s >> 16) % 0x800
    s = s * 0x41C64E6D + 0x3039; a = (a << 10) ^ ((s >> 16) % 0x400)
    s = s * 0x41C64E6D + 0x3039; a = (a << 10) ^ ((s >> 16) % 0x400)
    return a

def shuffle(doors, seed):        # doors：配对表，按登记顺序
    r = lcg_rand(seed)           # 只取一次，后面一直用同一个 r
    idx = list(range(len(doors)))
    while len(idx) > 1:
        a = idx.pop(r % len(idx))
        b = idx.pop(r % len(idx))
        doors[a].target = doors[b].door
        doors[b].target = doors[a].door
    if len(idx) == 1:            # 门数为奇数：剩下的单向指向 doors[r % n]（可能是它自己）
        doors[idx[0]].target = doors[r % len(doors)].door
```

- 种子是 `rand()`（0..32767）。所有客户端用同一个种子、同样顺序的配对表，算出同样的配对 [证实]。
- 收方在 3 个层管理器上各洗一次（`0x005FD788`），仲裁方本地只洗计时到期的那一层；目前的地图门都在同一层，结果一样 [证实]。

### 1.4 进门、等待、传送

**入口（本机控制的角色走进门格，事件 4，`0x00613E4D`）** [证实]：

1. 发 0x1176 `{EventID=5, PlayerID, Time, SrcRow=门行, SrcCol=门列, DestRow=门行, DestCol=门列}`。
2. `角色.SetPosition(col*40+20, row*40+20)`，吸到门中心。
3. `角色.vt+0x88`：锁输入（松开方向键）。
4. 创建 `effect/TransDoor_Enter.eff`，挂在角色 `+0x34C` 上；追加待处理项 `{pid, 2000, 8, 特效}`。
5. 最后调用基类处理（只有事件 1 才有作用）。

门不检查自己或角色的状态，也没有冷却：同一时刻可以有多个角色在同一扇门的待处理表里 [证实]。

**远端收到子类型 5（事件 5）**：同样吸到门中心，挂 Enter 特效，追加 `{pid, 2000, 8}`；不锁输入，也不发消息 [证实]。

**到期（门每帧 `0x00613D6E`）** [证实]：每项 `剩余时间 -= dt`，**≤0** 时：

- 如果 PlayerID 是本机控制的角色：`角色.vt+0x8C` 解锁输入；类型是 8 时，调用 `0x005D8E20(0xE, 门, 表项)`。
- 不论是不是本机：销毁特效，删掉这一项。远端角色的到期只是删特效，传送靠消息。

**传送（`0x005D8E20` 事件 0xE，`0x005D8E62`）** [证实]：

1. 在配对表里找这扇门的目标（`0x005D93E5`）；目标为 0 时什么都不做（角色已解锁，留在原门上）。
2. 发 0x1176 `{EventID=0xE, PlayerID=表项 pid, Time, SrcRow/SrcCol=入口门, DestRow/DestCol=出口门}`。
3. 调用出口门 `vt+0x48(0xE, G+0x3828)`。`G+0x3828` 是"当前处理的角色"，元素更新时它已被设回本机玩家（`0x005C87B0` 末尾）。

**出口门事件 0xE（`0x00613FD6`）** [证实]：

1. `SetPosition(出口中心)` 连调两次：上一位置也变成出口中心，下一帧不会被当成"走进了新格子"，所以**不会在出口门上再次触发**。
2. 是本机控制的角色时，`vt+0x88` 再锁输入。
3. 挂 `effect/TransDoor_Trans.eff`，追加 `{pid, 2000, 9}`；到期时本机角色解锁，类型 9 不再传送。

**远端收到子类型 0xE**：`0x005D8D93(0xE, 角色, DestRow, DestCol)`，即出口门对远端角色执行同一个事件 0xE：吸到出口中心、挂 Trans 特效、2000 ms 后删特效（不锁输入）[证实]。

**时间线（本机玩家）**：t=0 进门格，吸到中心并锁输入 → t=2000 解锁并立即瞬移到出口中心，再锁输入 → t=4000 解锁。共 **4000 ms** 不能操作，前 2 s 在入口，后 2 s 在出口 [证实]。

**没有做的事**（门的代码路径里没有）[证实]：不改朝向 `+0x3B4`，不改 `+0x3B8`，不设无敌，不检查角色是否活着。锁输入只是松开方向键并关掉输入开关，角色因为没有按键而停下 [推断]。所以等待期间能被炸 [推断]。离开出口门再走回来，或从别处走进任意一扇门，都会再次触发 [证实]。

**原版的小毛病**：出口门用的是 `G+0x3828`（本机玩家），不是表项里的 pid。仲裁方代管的 AI 走进门时，消息里是 AI 的 pid（远端会移动 AI），本地却会移动仲裁方自己的玩家 [证实代码；实际表现为推断]。复刻时建议按表项 pid 移动角色。

### 1.5 0x1176 NOTIFY_EVENT_MAP_ELEM

`QQTMsgData.bin` 里的记录（schema 0x1176，7 个字段，偏移 0x47BA4）[证实]：

| 偏移 | 字段 | 宽度 |
| --- | --- | --- |
| 0 | EventID | u16 |
| 2 | PlayerID | u16 |
| 4 | Time（`G+0x3838`，游戏时间） | u32 |
| 8 | SrcRow | u16 |
| 10 | SrcCol | u16 |
| 12 | DestRow | u16 |
| 14 | DestCol | u16 |

内存里正好是 16 字节。网络上按这个项目其它消息的惯例应是大端紧排 16 字节 [推断]；`internal/protocol/game/game_event.go` 已有常量 `NotifyMapElement = 0x1176`，服务端只放行，不解析 [推断]。

| EventID | 谁发 | 发送处 | 内容 |
| --- | --- | --- | --- |
| 5 | 走进门的本机角色的客户端 | `0x00613E65` | Src = Dest = 入口门 |
| 0xE | 同一客户端，2000 ms 后 | `0x005D8E62` | Src = 入口门，Dest = 出口门 |
| 0xD | 仲裁方，3 s 后每 30 s | `0x005D8B5F` | PlayerID = 仲裁方自己；SrcRow/SrcCol 没有初始化（栈上的垃圾值）；DestRow = `rand() >> 16`（总是 0）；DestCol = `rand() & 0xFFFF`；种子 = `(short)DestRow * 0x10000 + (short)DestCol` |
| 10 | 别的元素用（不是传送门） | `0x005D8F3F` | 非仲裁方转给仲裁方；仲裁方收到后发 0x0FA7（角色死亡） |

- 发送：`0x005A2F4C`（日志名 `CMessageLayer::AddLocalPlayerData`），和其它对局消息走同一条通道 [证实]。
- 接收：`0x005FD4E6`（虚表 `0x007A3EA8` 的 `+0x04`）。EventID 10 而且本机是仲裁方时另行处理；其余一律 `0x005D8D93(EventID, 按 PlayerID 找到的角色, DestRow, DestCol)`，三层各一次 [证实]。
- 收方不检查 PlayerID 是不是自己，所以发送方不能收到自己的回显，否则会传送两次 [推断]。

### 1.6 画面

- 门本身：初始化 `0x00613D4E` 把 `+0x20` 设成 `effect/TransDoor.eff`，再走基类初始化；因为 `+0x20` 已经有值，**不会**再创建普通元素的 `default_MapElement.eff`（`0x005EF283`）[证实]。特效点和普通元素一样：`(col*40 − offset.x + 8, row*40 − offset.y + 21)`（`0x005EEE71` 状态 1）[证实]。
- `TransDoor.eff`：两条 `magic8` 轨道（`object/magic/magic0008.img`，1 帧 152×152），位置 (24,17)，缩放 (0.45, 0.30)，透明度 0.6，白色；第二条轨道在 990 ms 缩到 (0.39, 0.24)，2000 ms 回到原样。尾部 `[1,0]`，应是循环播放 [推断]。也就是门下一圈每 2 s 呼吸一次的椭圆光。
- 门自己的 4 帧图 `elem26/29_stand.img` 不是这个对象画的；是否画在地图底图里没查 [未知]。
- `TransDoor_Enter.eff` 和 `TransDoor_Trans.eff` 的内容完全相同（逐字节比较）[证实]，挂在角色 `+0x34C` 上跟着角色走。轨道有 `magic40`×3、`magic41`×3（光点从 y=−10 升到 −60，然后在 −20 和 −60 之间来回，2500–2900 ms 升到 −150 并淡出，三条依次晚 200 ms）、`magic35`（21 帧，2000–2900 ms，旋转 180°）、`magic48`（27 帧，0–2890 ms，黄色 (255,255,128)，透明度 0.5）。尾部 `[0,0]`，不循环 [推断]。门的代码在 2000 ms 时销毁特效，所以 2000 ms 以后的关键帧**看不到** [证实]。
- 声音：门的代码里没有 [证实]。

## 2. 传送带 CMETransStrip

- 注册：`0x00614A5E`，大小 0x44；ID 17121–17128、17130–17133 映射到这个类（17129、17134 以后不是）[证实]。
- 虚表 `0x007A4C9C`：`+0x1C` 更新 `0x00614B3F`，`+0x48` 事件 `0x00614C49`；初始化、绘制用基类 [证实]。
- 构造 `0x00614AEB(id, data)`：`+0x38 = data[0]`（方向类型），`+0x3C = data[1]`（速度，float），`+0x40` 本帧 dt（ms）[证实]。
- `data` 由 `0x005CB4B7`（地图载入时按 ID 建元素）提供，速度一律 `0x3CA3D70A` = **0.02 像素/ms = 20 像素/秒**（每格 2 秒）[证实]。

### 2.2 位移函数 `0x00614CFF(x, y) → (x', y')`（反汇编核对）

`v = dt * 0.02`（`dt` 是这根带子本帧更新时存进 `+0x40` 的值）。`R`、`C` 是带子所在的行、列，`cell(p) = (int)p / 40`（向零取整），`canEnter(r, c, dir)` = `0x00614CA1` = 三层的 `0x005D8BC1(r, c, dir)` 全为真（只看地图元素，不看泡泡、角色）[证实]。

直线（ID 用到的只有这 4 种）[证实]：

| 类型 | 规则 |
| --- | --- |
| 0 右 | 若 `cell(x+20) == C`（还没到格子中心）：`x += v`；否则只有 `canEnter(R, C+1, 0)` 时才 `x += v` |
| 1 上 | 若 `cell(y−20) == R`（还在中心或以下）：`y −= v`；否则只有 `canEnter(R−1, C, 1)` 时才 `y −= v` |
| 2 左 | 若 `cell(x−20) == C`：`x −= v`；否则只有 `canEnter(R, C−1, 2)` 时才 `x −= v` |
| 3 下 | 若 `cell(y+20) == R`：`y += v`；否则只有 `canEnter(R+1, C, 3)` 时才 `y += v` |

也就是：在格子里往中心走时不受阻挡；过了中心，要前方格子能进才继续推，前方是墙就停在中心。每次只改一个坐标，另一个坐标不对齐。

转角类型 4–11 代码里有，但没有 ID 用（`0x005CB4B7` 只给出 0–3）。记下来备查 [证实]：

| 类型 | 先 | 再 |
| --- | --- | --- |
| 4 | `cell(x+20)==C` 时右移 | 否则按"上"处理（`cell(y−20)==R` 时自由，否则查 `canEnter(R−1,C,1)`） |
| 5 | `y−20>0` 且 `cell(y−20)==R` 时上移 | 否则按类型 0 |
| 6 | `cell(x+20)==C` 时右移 | 否则按"下"处理 |
| 7 | `cell(y+20)==R` 时下移 | 否则按"右"处理 |
| 8 | `x−20>0` 且 `cell(x−20)==C` 时左移 | 否则按类型 1 |
| 9 | `y−20>0` 且 `cell(y−20)==R` 时上移 | 否则按类型 2 |
| 10 | `x−20>0` 且 `cell(x−20)==C` 时左移 | 否则按类型 3 |
| 11 | `cell(y+20)==R` 时下移 | 否则按"左"处理 |

### 2.3 推什么

**泡泡**：每根带子每帧（`0x00614B3F`）[证实]：

1. `+0x40 = dt`。
2. 从泡泡管理器（`G+0xF40`，`0x005D3BD3(R, C)`）取这一格的泡泡列表（这个管理器打印 "BOMB FOUNDED"，`0x005D3DE8`）。
3. 只推状态 `+0x2C == 1` 的泡泡（1 = 放在地上，`0x005DF6FB`；被踢飞/移动中是 3，`0x005DF724`，不推）。
4. 泡泡位置是 `+0x3C/+0x40`（x/y，`0x005DF9B5`）。算出新位置后，若新位置所在格不是这根带子的格子，就把泡泡挪到新格（`0x005D3C77`：移出、`0x005DF590` 改格子并吸到新格中心、再放回），然后用 `0x005DF9CA` 把位置改回连续坐标。
5. 不发任何消息：每个客户端各推各的泡泡，靠大家初始状态和 dt 一致 [证实没有消息；同步效果为推断]。
6. 泡泡离开最后一格带子、进入普通格时，那一格没有带子再推，泡泡停在刚越过格子边界的位置（离新格中心约 20 像素）[由代码推出，推断]。

**角色**：带子收到事件 6（角色站在这格，见 0.4）时（`0x00614C49`），用同一个函数算新位置，`角色.SetPosition(x', y')` [证实]。

- 只有本机控制的角色才会产生事件 6，所以每个客户端只推自己的角色（仲裁方还推代管的 AI），远端角色的位置靠它自己客户端的移动同步 [证实事件来源；同步为推断]。
- 用的 dt 是带子自己上一次更新存的 `+0x40` [证实]。
- 事件 6 不看角色状态，被泡住、阵亡的角色也会被推 [证实代码路径；实际表现为推断]。
- 推动不检查泡泡和其他角色，只检查地图元素 [证实]。
- 角色自己走的位移另外算，两者叠加 [推断]。

**道具**：不推，带子只遍历泡泡列表 [证实]。

## 5. 给复刻的建议（Go 对战引擎 + Python 客户端）

1. **传送门**由引擎判定：角色中心在本帧走进门格（上一帧在别的格子，而且是自己在走）→ 吸到门中心，锁输入 2000 ms → 按当前配对瞬移到出口中心（上一位置一并改成出口中心）→ 再锁 2000 ms。没有配对时只解锁。不设无敌，不改朝向。
2. **配对**：每层按行优先登记；开局 3000 ms 第一次洗牌，之后每 30000 ms 一次，种子取 0..32767。和原版客户端同局时，要发或接受 0x1176/0xD，并照 1.3 的 LCG 算法算配对。
3. **动画**：入口和出口各挂 2000 ms 的 TransDoor_Enter（两个文件相同），跟着角色；门下是循环的 magic8 椭圆光。远端客户端靠 0x1176 的 5 和 0xE 播放。
4. **传送带**：每帧 `dt × 0.02` 像素，按 2.2 的规则推本格中状态为"放在地上"的泡泡和站在格子上的角色，只看地图元素是否可进入。要和原版逐帧一致，就必须用每根带子自己的 dt，并且不对齐另一个坐标。
5. 和原版客户端同局时，泡泡被推是各端各算的，没有消息；角色被推之后的位置靠普通移动同步。
