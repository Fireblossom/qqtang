# 类型 11 的 2×2 大泡与类型 12 的陪泡（Client.exe 静态逆向）

范围：鲁尼 / 小小罗的技能 12（0x1169）和规则 2 空投（0x10E1）放出的"大泡"，场景对象 / 泡类型 11，以及只在空投里出现的类型 12。
前文：`boss-kickbomb-re.md` §4.3（选格 `0x005B8753`）和 §5（0x1169 接收方），`cmd/qqt-battle-sidecar/kickbomb.go` 的头注释（空投调度）。这些内容这里不再重复。

标注沿用前文：**[汇编]** 已用 capstone 核对原始指令；**[伪C]** 只读了 Ghidra 伪 C；**[推断]** 有依据但没有完全追到。地址都是 Client.exe 的虚拟地址。

## 0. 结论摘要

1. **泡管理器里没有"2×2"这个概念。** 每个泡只登记在自己的一格（`+0x28` 行、`+0x2a` 列）。除了绘制锚点（`0x005DF6FB`）、踢泡（`0x005B4506`、`0x0060CF49`）和足球寻路器（`0x005E0351`）以外，全程序没有别的代码区分类型 11/12（全量扫描 `cmp [reg+4], 0xb/0xc`，结果见 §8 附录）。
2. **技能 12（0x1169）只建 1 个类型 11 的泡**，放在 2×2 空地的右下格（锚点）：
   - 只有锚点格挡路，另外 3 格可以走，也可以放泡、落泡；
   - 爆炸就是从锚点出发的普通十字，威力字段 8，每臂最长 7 格；
   - 画面上那张大图（`bomb11_stand.img`，锚点 (45,70)）盖住整个 2×2 块，但只是图。
3. **空投（0x10E1）的类型 11 会额外配 3 个类型 12 的"陪泡"**，放在另外 3 格（左上、正上、左边）。陪泡和主泡用同一个主人、同一个时间、同一个威力 8。
   - 主泡以 400 px/s 从行端飞入，陪泡以 **10 px/s** 从行端飞向目标格 [汇编]，3 s 内只能挪约 30 px，飞行中不挡路，自己也不会引爆；
   - 主泡一炸，陪泡通过连锁一起炸。结果是 4 个重叠的十字，也就是宽 2 格的十字，每臂最长 7 格；
   - 类型 12 的图 `bomb12_stand.img` 与 `bomb11` 的像素完全相同，画的时候用普通泡的锚点 (0,15)，原版画面上大概会看到 3 张大泡图从行端慢慢爬进来（见 §8 第 1 条）。
4. **引信：所有泡都是 3000 ms，从本端建泡时算起，与类型无关** [汇编]。
   - `boss-ai-re.md` 说 `G+0xF88`（2990/2500）是引信，这一点要更正：`G+0xF88` 是 AI 危险表的门槛（`0x005DF875`）；
   - 真正的爆炸判断是 `0x005DF7D0`：`+0x2c == 1`（已落地）并且 `+0x30 < 0`；
   - `+0x30` 在 `0x005DF496` 设为 3000，每次更新减去 dt（`0x005DF518`），飞行中照样减。
5. **爆炸、连锁、炸墙、火焰图、命中都和普通泡完全相同**：
   - 0xFA4 记录里的类型字节是 11 或 12；
   - 火焰图用 `object/flame/flame1..9`：中心 1，左臂 4、左端 8，右臂 2、右端 6，上臂 3、上端 7，下臂 5、下端 9；
   - 命中仍然是每条 0xFA4 消息对本机玩家判一次（5 点采样）。
6. 线上字段：
   - 0x1169 技能 12 的每项是 `{u32 SceneID=11, u8 row, u8 col}`，泡类型取第一项的 SceneID；
   - 0x10E1 的每个泡是 `{u32 SceneID=11, u8 power=8, u8 row, u8 col}`，排在普通泡和威力泡前面。
   - 陪泡**不上线**，由每个接收方根据类型 11 自己补建。

## 1. 泡对象（`0x005DF3D1` 构造，0x44 字节，虚表 `0x007A35CC`）

工厂 `0x005CB087()` → `0x005CC58F(type, p2, p3)`：构造后立刻调虚表 `+4` = `0x005DF496` 初始化，失败就析构并返回 NULL。

| 偏移 | 含义 |
|---|---|
| `+0x04` | 泡类型（= 场景对象号：1 普通、2 威力、9 雕像规则、11 大泡、12 陪泡、13/14 机关规则……） |
| `+0x08/+0x0C` | 工厂的 p2/p3。`0x004255D0(p2,p3)` 把它们换成特效路径，路径非空就在 `+0x10` 挂一个特效。技能 12 传 Boss 的 `role+0x400` 对象 `+0x274/+0x278`，空投传 0/0 |
| `+0x10` | 附带特效（可空） |
| `+0x14` | 精灵对象，对象号 `0x03000001 \| type<<8`（类型 3 = 泡，动作 1 = stand），见 §5 [汇编] |
| `+0x18` | 飞行对象（`0x005A489E`，虚表 `0x007A1B0C`），飞完就删除 |
| `+0x1C` | 主人 ID（u16） |
| `+0x1E` | 威力（u16），实际臂长上限是威力 − 1（§4.2） |
| `+0x20` | `role+0x400` 对象的虚表 `+0x24` 返回值，只在危险表里累加（`0x005D434C`：`entry+8 += +0x20`），与爆炸无关 |
| `+0x24` | 放置时间（消息里的 Time）。接收 0xFA4 时按（格子、时间）找泡 |
| `+0x28/+0x2A` | 行、列（i16）；飞行时已经是**目标格** |
| `+0x2C` | 状态：1 已落地（`0x005DF6FB`），3 飞行中（`0x005DF724`） |
| `+0x30` | 剩余引信，初值 3000 |
| `+0x34` | 泡管理器（G+0xF40） |
| `+0x3C/+0x40` | 像素坐标（float），格心是 `col*40+20`、`row*40+20` |

虚表：`+0x0C` 绘制 `0x005DF543`（格子上有地图元素时不画）、`+0x10` 图层 `0x005DF57F`（落地 20，飞行 60）、`+0x14` 更新 `0x005DF518`、`+0x18` 落地 `0x005DF6FB`、`+0x1C` 起飞 `0x005DF724`。

## 2. 占格、挡路、放泡

### 2.1 管理器只按一格登记 [伪C，入口参数已用汇编核对]

- `0x005D388A(b, row, col)`：键是 `row<<16 | col`；传 `0xffff` 时用 `b+0x28/+0x2a`。只登记这一格。
- `0x005D3BD3(row, col)` 返回该格的泡列表。挡路、放泡、选格、炸到泡，查的都是这张表。
- 移除 `0x005D3A9D`、重新登记 `0x005D3C1D`（先移除，再起飞，最后在目标格登记）里都没有按类型扩展格子的代码。

### 2.2 挡路 [伪C]

移动碰撞 `0x005B7999` → `0x005B7DC7` → `0x005B7E31(row, col)`：目标格里只要有一个 `+0x2c == 1` 的泡就挡。`0x005B7F5C` 是通用的"人已经站在泡格里时可以走出去"的豁免。所以：

| 场景 | 挡路的格 |
|---|---|
| 技能 12 的大泡 | 只有锚点（右下格）。左上、正上、左边三格照常可走，人可以"走进"大泡图里 |
| 空投的大泡 | 主泡落地后挡锚点；3 个陪泡一直在飞（10 px/s，3 s 内到不了），所以**一直不挡路** [推断：按速度算出来的，见 §6.2] |

- 没有任何推人的代码。
- 选格 `0x005B8753` 只检查地图元素、泡、特殊场景物、地面道具，**不检查玩家**，所以大泡可以落在玩家身上。玩家站在锚点上时，与站在刚放下的普通泡上相同（可以走出来，不能再走回去）。

### 2.3 放泡 / 落泡 [推断]

各种"这格能不能放泡"的判断都查 `0x005D3BD3` 的列表是否为空，所以：
- 技能 12 大泡的另外 3 格算空格：之后的空投、踢飞的泡都能落进去（`0x005B8753` 的空格表、`0x005B438D` 的踢泡落点都只按这张表或地图元素判断）；
- 空投大泡的 3 格被陪泡占着（陪泡一登记就在目标格）。

规则 2 玩家本来就不能放泡，这一条只影响空投和踢泡。

### 2.4 踢泡

踢泡命令 `0x0060CF49`（`0x0060D0B8`）、`kickable` `0x005B4506`（`0x005B4544`）、足球寻路器的 `passable5`（`0x005E08B0`，比较在 `0x005E0981`）都把 0x0B、0x0C 排除在外：大泡和陪泡都踢不动，寻路时算阻挡。

## 3. 引信（更正 `boss-ai-re.md` 第 8 条） [汇编]

| 函数 | 作用 | 判断 |
|---|---|---|
| `0x005DF496` | 初始化 | `mov [esi+0x30], 0xbb8`（3000） |
| `0x005DF518` | 每帧更新 | 状态 1 或 3 时先更新精灵或飞行，然后**无条件** `sub [esi+0x30], dt` |
| `0x005DF7D0` | **爆炸判断** | `+0x2c == 1` 并且 `+0x30 < 0`（`cmp [esi+0x30],0; jge`）。规则 7 另有：格子上有 0xC9 道具时把 `+0x30` 改成 10 |
| `0x005DF875` | 危险表门槛 1 | `+0x2c == 1` 并且 `+0x30 < mgr+0x48`（G+0xF88，默认 0xBAE = 2990，`0x005D3511`）时返回 1 |
| `0x005DF916` | 危险表门槛 2 | `+0x2c == 1` 并且 `+0x30 ≤ 799` |

- 调用关系：仲裁方的规则组件 `0x0060E720` 判断自己是仲裁方（`S+0x4b34 == S+0x4b40`）后，按 `0x00534AD0(本机 ID)` 的结果二选一（`0x0060E77D`～`0x0060E7A5` [汇编]）：
  - 返回 0：调 `0x005D4937`（用 `0x005DF7D0` 找出到时的泡并引爆，然后发 0xFA4）；
  - 返回非 0：调 `0x005D3668`/`0x005D4248`/`0x005D4142`，只建危险表（用 `0x005DF875`/`0x005DF916`）。
  - 这个返回值的含义没查，可能是"本机已阵亡或在观战"[推断]。
- 结论：**引信是固定的 3000 ms**，以仲裁方本端建泡的时刻为起点。泡要已经落地；飞行时间也计入引信。这与录像吻合：`other-rules.md` 记录批次 5000 ms 的空投泡在 8032 ms 爆炸。
- `G+0xF88`（AI 改成 2500）只影响"泡已经点着多久就算危险"，不改变引信。
- 类型 11/12 没有特殊引信。
- 技能 12 从起飞到落地只有一帧（起点等于终点，`0x005A45CE` 直接置完成），实际约 3000 ms 加一帧后爆炸。

## 4. 爆炸

### 4.1 选出要炸的泡 `0x005D4937` [伪C]

1. 种子：所有泡中 `0x005DF7D0` 返回 1 的（已落地、引信到时）。
2. 连锁：把种子的连锁表里的泡逐个加进去，加进来的泡的连锁表也展开，直到不再增加（传递闭包）。**不检查被连锁的泡是否已落地**，飞行中的泡也会被连锁引爆。
3. 对每个泡调 `0x005D434C(b, 1)` 生成爆炸记录和火焰格。
4. 遍历火焰格：地图元素调虚表 `+0x34`（受击）；地面道具也会被炸掉，例外是 0x2C、0x2E、0xC9、0x50、0xCB、0xCC 这几种，以及格子上有地图元素的情况。

连锁表在登记时就建好（`0x005D388A`）：新泡和每个已有的泡互相判断 `0x005D3EC1(a, b)`，"a 能炸到 b"就把 b 放进 a 的表。`0x005D3EC1` 的规则：
- 同行或同列，并且 `dist ≤ 0x005D476F(a, 方向)`（a 在那个方向的臂长）；
- 不同行也不同列一律炸不到；
- 同一格（dist 0）算能炸到。
- 类型 0xD、0xE 另有特例，与 11/12 无关。

### 4.2 臂长 `0x005D476F(b, dir)` [汇编核对尾部]

- 方向码：0 右（列 +1）、1 上（行 −1）、2 左（列 −1）、3 下（行 +1）。
- 从泡所在格逐格往外走：
  - 出界就停；
  - 遇到**任何泡**（表里有，不管状态和类型）就停，这一格算在臂长里；
  - 遇到不可穿透的地图元素就停：可炸元素那一格算在内，不可炸的不算（`0x005D8C3C`、`0x005D8CB7(…,4)`）。
- 结果上限是**威力 − 1**（`0x005D4926: mov eax,[ebp-0x18]; dec eax`）。大泡威力 8，每臂最长 7 格。这与 sidecar 空投用的 `Power = wire − 1` 一致。

### 4.3 爆炸记录 `0x005D434C` [汇编核对分支]

类型只在 `0x005D440A` 处分支：`sub eax,0xd; je`（0xD：4×4 方块）、`dec eax; je`（0xE：半张图，规则 7）。**11 和 12 走普通十字**，没有加宽，没有按 2×2 展开。

0xFA4 里每条记录 13 字节，与这里的结构一一对应：

| 偏移 | 内容 |
|---|---|
| +0 | u16 主人 |
| +2 | u32 放置时间 |
| +6 | u8 泡类型（11/12 原样带上） |
| +7 | u8 行 |
| +8 | u8 列 |
| +9 | u8 上端行 |
| +10 | u8 下端行 |
| +11 | u8 左端列 |
| +12 | u8 右端列 |

### 4.4 两种大泡的实际火焰

- **技能 12**：一个以锚点 (r,c) 为中心的普通十字。2×2 图里的左上格 (r−1,c−1) **不会着火**；(r−1,c) 和 (r,c−1) 只是作为上臂、左臂的第一格着火。
- **空投**：主泡在 (r,c)，陪泡在 (r−1,c−1)、(r−1,c)、(r,c−1)。四个泡互相在臂长 1 内（相邻格有泡，臂就停在那一格并把它算进去），所以四个全进连锁闭包，一起炸。

  每个泡的臂遇到相邻的泡就停，所以四个十字合起来的形状是：
  - 行 r−1 和行 r 各有一条横向火焰，从 2×2 往左右各延伸最多 7 格；
  - 列 c−1 和列 c 各有一条纵向火焰，往上下各延伸最多 7 格；
  - 2×2 本身四格都着火。

  每个泡的每条臂各自在第一个可炸物处停下并炸掉它。

  > 细节：泡 (r−1,c) 往下走一步就碰到 (r,c) 的主泡，所以这条臂长 1；往上不受影响。其余三个泡同理。整体就是宽 2 的十字。

- 一帧里同时爆的所有泡放在**同一条 0xFA4** 里（`0x0060E720` 最多打包 0x9C0 条），所以空投大泡是 4 条记录，类型字节分别是 11、12、12、12。

### 4.5 接收 0xFA4（`0x00606F28`）[伪C，早退一处已用汇编核对]

每条记录依次执行：
1. 在 (行, 列) 的列表里找 `+0x24 == 时间` 的泡并移除。
2. 类型不是 9、0xD、0xE，并且规则不是 8 时，查主人角色 `0x005A287F(主人)`，然后 `role->0x005AE052(1)`（归还一个泡容量）。
   - **主人查不到就 `je 0x6075BF` 直接退出整条消息**：后面的记录、火焰、炸墙（`0x006075D0`）、命中判断（`0x00607899`）、NPC 判定都不做了 [汇编 `0x00607074`]。
   - 11 和 12 都走这一步。技能 12 的主人是 Boss：Boss 在大泡爆炸前从角色表里消失的话，就会触发这个早退。原版有这个隐患，见 §8。
3. 生成火焰：中心 `flame1`；左端 `flame8`、左臂 `flame4`；右端 `flame6`、右臂 `flame2`；上端 `flame7`、上臂 `flame3`；下端 `flame9`、下臂 `flame5`。
   - 火焰对象工厂 `0x005CC605`；图是 `object/flame/flame<k>_stand.img`。
   - **没有按泡类型换火焰图**。`flame10` 属于别的规则，与类型 11/12 无关。
4. 每个火焰格再调 `0x005D3E64(行,列)`，把格里剩下的泡全部删掉（规则 12 除外）。

所有记录处理完以后：
- `0x006075D0` 炸墙；
- `0x00607760`；
- `0x00607899` 判断本机玩家：取玩家位置和 ±3 px 的四个角共 5 点，查这些点所在格有没有火焰对象，5 点里至少 4 点着火就进入被困（`0x00607A23`）。**每条消息只判一次**，所以四个十字重叠也只困一次；
- 仲裁方再对每个 NPC 调 `0x00607DDC`（Boss 每条消息固定扣 1 HP，见 `boss-lifecycle-re.md`）。大泡同样能炸到 Boss 自己。

## 5. 绘制

### 5.1 图像 [从资源核对]

`data/object.pkg` 里的帧信息（用 `qqtclient/dimg.py` 解出）：

| 文件 | 画布 | 帧（x, y, 宽×高） |
|---|---|---|
| `object/bomb/bomb11_stand.img` | 86×83 | 4 帧：(7,36) 75×74、(6,27) 71×83、(7,36) 75×74、(1,41) 86×69 |
| `object/bomb/bomb12_stand.img` | 88×114 | 4 帧，偏移、尺寸、**像素都与 bomb11 完全相同**，只有画布不同（画布不参与定位） |
| 对照 `object/bomb/bomb1_stand.img` | 44×42 | 4 帧：(3,18) 38×37、(3,13) 36×42、(3,18) 38×37、(0,20) 44×35 |

帧的排列与普通泡相同（1、2、1、3 的呼吸节奏），所以帧时间可以沿用普通泡，原生客户端里是 `clock // 150` [推断：帧时间在 GFX 引擎里，没追]。精灵对象落地时调虚表 `+0x1c` = `0x005C4927`，即循环播放动作 1。

### 5.2 锚点 `0x005DF6FB` [汇编]

```
mov byte [esi+0x2c], 1 ; 精灵->vtbl[0x1c]()
cmp dword [esi+4], 0xb ; jne → push 0xf, push 0     → 锚点 (0, 15)
                       ; 否则 push 0x46, push 0x2d  → 锚点 (45, 70)
```

- **只有类型 11 用 (45,70)**，类型 12 和其他所有泡都用 (0,15)。
- 屏幕位置 `0x005C477E` / `0x005C48D9` 的公式：`x = 格心x − 锚点x − 镜头x − 12`，`y = 格心y − 锚点y − 镜头y + 1`。
- 原生客户端用的是 `ox + col*40 − ax + 帧x`、`oy + row*40 − ay + 帧y`（普通泡已按这个公式和录像校准，`scene.py` 的 `BOMB_ANCHOR`）。代入类型 11 的第 0 帧：
  - x 从 `col*40 − 38` 到 `col*40 + 37`，以锚点格的左边线为中心，横跨 c−1、c 两列；
  - y 从 `row*40 − 34` 到 `row*40 + 40`，底边对齐锚点格底边，高约 2 格。
  - 正好盖住以锚点为右下角的 2×2 块。
- 普通泡第 0 帧在 `col*40+3..+41`、`row*40+3..+40`，同样是底边对齐，两者一致。

移植时：类型 11 画 `bomb11_stand.img`，锚点 (45,70)，其他与普通泡相同。

### 5.3 类型 12

- 画 `bomb12_stand.img`，锚点 (0,15)。
- 图层：飞行时 60，落地 20（`0x005DF57F`）。
- 绘制由每格的绘制函数 `0x005E6B21` 按 `0x005D3BD3` 的列表收集，不看类型。坐标取飞行对象的当前位置（`0x005DF67C` → `0x005C477E`）。
- 所以静态看，空投大泡的 3 个陪泡**会被画出来**：三张大泡图从行端以 10 px/s 爬进来（3 s 约 30 px），然后在爆炸时消失 [推断，没有录像核对，见 §8]。

## 6. 线上字段与接收方

### 6.1 0x1169 技能 12 —— 接收 `0x005FDB18` 的 case 0xC（`0x005FDF84`～`0x005FE057`）[汇编]

消息体：

| 偏移 | 内容 |
|---|---|
| 0 | u16 ObjectID（Boss） |
| 2 | u32 Time |
| 6 | u16 PosX |
| 8 | u16 PosY |
| 0xA | u16 SkillID |
| 0xC | u8 Count |
| 0xD 起 | Items，每项 6 字节 `{u32 SceneID, u8 row, u8 col}` |

接收方的做法：
1. 先把 SkillID 改写成 0xC（`mov word [esi+0xa], 0xc`，无副作用）。
2. 要求 `Count ≤ 0x40`。
3. **泡类型取 `Items[0].SceneID`**（`[esi+0xd]`），后面各项的 SceneID 不看。
4. 对每一项：
   - `0x005CC58F(type, boss+0x400 → +0x274, +0x278)` 建泡；
   - `+0x1c = ObjectID`，`+0x24 = Time`，`+0x1e = 8`（写死，与消息无关）；
   - `0x005DF590(row, col)`；
   - `+0x20 = boss+0x400 → vtbl[0x24]()`；
   - `0x005D388A` 登记；
   - `0x005D3C1D(b, row, col, 400, 0)`：起点等于终点，一帧后落地。
5. **不建类型 12 的陪泡**，不消耗随机数。

### 6.2 0x10E1 空投 —— 发送 `0x0061988B`，接收 `0x006018A7` [汇编]

消息体：

| 偏移 | 内容 |
|---|---|
| 0 | u16 主人（仲裁方 `+0x328`） |
| 2 | u32 Time |
| 6 | u8 泡数（接收方按有符号 char 比较） |
| 7 起 | 泡表，每个 7 字节 `{u32 SceneID, u8 power, u8 row, u8 col}`，最多 32 个 |
| 0xE7 | u8 道具数 |
| 0xE8 起 | 道具表，每个 6 字节 `{u32 SceneID, u8 row, u8 col}` |

发送方：
- 大泡个数 `n = 0x005E1856()`：时间 < 120000 ms 时为 0；否则 `r = RNG % 1000`，`r == 100` 得 3，`r ∈ {201, 202}` 得 2，`r ∈ 300..304` 得 1，其余为 0。
- 选格 `0x005B8753(普通+威力+道具总数, single, n, big)`，大泡**先选**，所以普通泡不会落在大泡的 2×2 上。
- 泡表里大泡**排在最前**，每个 `{11, 8, row ≤ 12, col ≤ 14}`。`0x00619C6E` 跳过出界或有地图元素的格（`big` 来自空格表，实际不会跳过）。
- 泡数字段最后改写成"大泡数 + 普通泡数 + 威力泡数"。

接收方对**每个泡**（不分类型）的处理：
1. `0x005CC58F(SceneID, 0, 0)` 建泡（返回值不判空）；`+0x1c` = 主人，`+0x24` = Time，`+0x1e` = power。
2. `0x005A287F(主人)` 查不到时，读 `[0x400]`（对空指针 +0x400 取值），会崩溃。也就是说主人必须是一个存在的角色；查得到时 `+0x20` 保持 0。
3. **消耗 1 次场景随机数** `0x0040F722(S+0x10)`：奇数时起点列 = 0，偶数时 = 14（各端同步）。
4. `0x005DF590(row, 起点列)`，`0x005D388A` 登记，`0x005D3C1D(b, row, col, 400, 0)` 飞到目标格。

SceneID 为 11 时（`0x006019BA: cmp [esi-5], 0xb`）再建 3 个类型 12，主人、时间、power 都相同：

| 陪泡 | 起点 | 终点 | 速度 |
|---|---|---|---|
| 1 | (row−1, 起点列) | (row−1, col−1) | **10** |
| 2 | (row−1, 起点列) | (row−1, col) | **10** |
| 3 | (row, 起点列) | (row, col−1) | **10** |

- 速度是 `push 0xa`，在 `0x00601A3B`、`0x00601AE0`、`0x00601B6C` 三处；主泡是 `push 0x190`（400）。
- 飞行对象的速度单位确实是 px/s：`0x005A467D` 里 `step = speed * dt * 0.001`。
- 陪泡用同一个起点列，**不再消耗随机数**。
- 陪泡 1 建失败时整条消息直接返回（`je 0x601c27`），陪泡 2、3 建失败只跳过本泡。
- 道具部分照旧：从 (0, col) 以 400 px/s 落到 (row, col)。

由此（按速度推算）：
- 陪泡要飞 `|col − 1 − 起点列| × 40` px 或 `|col − 起点列| × 40` px，10 px/s 下要几十秒，3 s 引信内到不了；
- 它们一直是状态 3：不挡路，自己不会引爆；
- 但从一开始就登记在目标格，所以会挡住火焰（臂走到它们那一格就停），也会被主泡连锁引爆（§4.1）；
- 爆炸记录用的是 `+0x28/+0x2a`，也就是目标格，火焰出现在 2×2 上，而不是陪泡图当时所在的位置。

## 7. 移植清单（Go 引擎 / sidecar）

1. **泡类型**：`Bomb.NativeStyle = 11/12`。
   - 占格、碰撞、连锁、放泡判断都按单格处理，与普通泡相同；
   - 踢泡和足球寻路器要排除 11、12（AIType 5 的 A* 把它们当墙）。
2. **技能 12**：每项在 (row,col) 建一个 `{style 11, power 8, owner Boss, placedAt Time}`，原地落下（一帧后落地），不建陪泡，不消耗随机数。取 `min(n, len(single), len(big))` 防越界（`boss-kickbomb-re.md` §4.3）。
3. **空投**：`0x005E1856` 的概率表；大泡排在泡表最前，wire power 8。
   - 接收：主泡按现有 `DropRuleBatch` 处理（400 px/s，从行端飞入，消耗 1 次随机数），另外补 3 个 style 12，飞行速度 0.01 px/ms，起点列与主泡相同；
   - 引擎要允许"飞行中被连锁引爆"，至少对 style 12 要这样，否则陪泡永远炸不了。原版对所有泡都是这样（§4.1）；现在 `rule_drop.go` 写的是"落地前不能爆炸"，只覆盖了自己引爆这一半。
   - 0xFA4 记录照常为每个泡发一条（类型字节 11/12）。
4. **臂长**：`Power − 1`。8 → 7，与空投普通泡的换算相同。
5. **引信**：3000 ms，从放置时刻起算，要求已落地。若引擎现在用 2990，以 3000 为准（§3）。
6. **火焰**：类型 11/12 用普通的 flame1～9，不用 flame10。
7. **绘制**（`qqtclient/battle/scene.py`）：
   - style 11 画 `bomb11_stand.img`，锚点 (45,70)；
   - style 12 若照原版，画 `bomb12_stand.img`，锚点 (0,15)，位置取飞行中的位置。若想更好看，也可以隐藏（`Invisible`），但这偏离了原版，要在提交里说明；
   - 帧时间与普通泡相同。
8. **0xFA4 主人查不到时整条消息作废**是原版隐患。移植时建议记一条警告，照常处理（不要复制崩溃或早退），但要知道这可能让双端不一致。

## 8. 待查 / 未证实

1. **陪泡在原版画面上是否真的可见**：静态看会画（图不透明，锚点 (0,15)，10 px/s 从行端爬入）。要有 120 s 以后出大泡的录像才能核对；空投大泡每局出现的概率只有约两成（120～240 s 约 30 批，每批 0.8%），`Tutorial3.qbv` 只有 131 s。也无法排除 10 是笔误、本意是别的速度。
2. **`0x00534AD0(id)` 的含义**（决定仲裁方本帧是真引爆，还是只建危险表）。
3. `0x005D388A` 建连锁表时，"a 能炸到 b"和"b 能炸到 a"分别存进谁的表，Ghidra 丢了 `this`，只读了伪 C。四个泡互相相邻，两个方向都成立，所以对本文结论没有影响。
4. 连锁表只在登记时计算一次，之后墙被炸开、别的泡被移走都不会更新（除了 0xD/0xE 会触发 `0x005D3FEE` 全量重算）。这是所有泡的通用行为，引擎是否照此实现要另查。
5. `+0x20`（`role+0x400` 的虚表 `+0x24`）和工厂 p2/p3（Boss 的 `+0x274/+0x278` 特效）对 Boss 实际是什么值没查。影响 AI 危险表的累加值，以及大泡是否带附加特效。
6. 帧时间（150 ms）沿用原生客户端的普通泡，没有在 GFX 引擎里核对。
