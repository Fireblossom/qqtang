## 入口与候选地板

构造 `0x00618ABF`，虚表 `0x007A4E14`，类型函数 `0x00618B05` 返回 3：逐帧控制器，无消息参数。虚表 `+8` 为 VM 入口 `0x00888505`（`0x00618B96` 跳到此处）。以前列出的 `0x00618D0F` 是保护代码中间片段，不能独立调用。

`0x00618EF5` 初次运行时扫描地面层 `S+0x21D4` 的 13×15 格。对非空对象调用虚表 `+0x24(6)`，列 0～5 入左池、9～14 入右池，中间三列不入池；坐标复制对象 `short row/col`（`+8/+A`），保留扫描顺序。

普通元素的 `+0x24` 为 `0x005EF340`，类型 6 检查属性 `canMove & 0x10`。安装包补给地板 **13015** 设置此位，并非任意空地。地图解析新增 `CompetitiveMap.MachineSupplyCells`，读取第三层正锚点和配置尺寸的投影；负数编辑器标记不创建对象。未改原始资源。

## 生产流程

只由仲裁方运行。`L/R` 为两池数量，`N` 为场景玩家指针向量长度：

```text
N <= 0 或 L+R <= 0：结束本帧
interval = 240000 / (14*(L+R) + 3*N)      // 正整数除法截断
Cool 已毁半场：清空对应池，之后不恢复
依次处理左、右：
  本池为空或 now-last[side] < interval：跳过本半场
  遍历本池，任一格地面道具列表非空：跳过本半场
  cell = pool[RNG % len(pool)]
  scene = 按下表抽签
  scene == 0：结束整个本帧，不处理右侧、不更新 last
  last[side] = now
  发送 0x115A，本机分发同一消息
```

公式已从 VM 实际执行的 `0x00890940..0x0089096B` 确认：两池总数乘 14，玩家数乘 3，分子 `0x3A980=240000`，`idiv ecx`。计算在清 Cool 池之前，因此清池当帧仍用旧总数，后续帧用缩小后的池。两半场最后成功时间在组件 `+0x34/+0x38`，初值 0。

人数只读 `S+0x264C/2650` 向量长度。最终人数探针监控玩家对象读取，结果零次；不按存活或队伍计数。移植使用尚未离场的参赛者数。

占用仅查询 `S+0x2220 = M+0xF10` 地面道具管理器（`0x005D9B59`）。不查人物、泡、火焰、墙层；也不是随机到已占格再重抽。任一补给格已有道具，就暂停整个半场，另一半场仍可生成。

`0x00618E1E` 用 RNG `%100`：

| 半开区间 | 结果 |
| --- | --- |
| [0,30) | 不生成，整帧早退 |
| [30,60) | 1：小泡数 |
| [60,85) | 2：小威力 |
| [85,100) | 3：小速度 |

`S+0x4C50/51 = M+0x3940/41` 为 Cool 已毁设备标志，不是队伍色或人数；写入来自 `0x006081A6/0x006081D6`，会永久清空对应池。

## 消息与接收

`0x115A NOTIFY_PRODUCE_ITEM` 的消息体是 `u8(row<<4|col), u32(ItemID)`，没有时间。模拟器对象小端，网络 ItemID 大端，复用既有 `game.ProduceItem` 编解码。

接收 `0x005FF1F9 → 0x005FF230`：创建/初始化（`0x005CB087`、`0x005CB79A`）、定位（`0x005CCE0A`）、直接注册进地面管理器（`0x005D9A79`）。**立即落地，无小鸟/飞行等待**。引擎新增默认关闭的 `NativeMachineSupply` 和显式生成方法，只允许 1～3。

sidecar 发 UDP Type-2 消息及既有 TCP 可靠副本。跟随端只认当前仲裁方，保存消息头时间为每半场最后生成时间；忽略重复/较旧包，出现新补给时清理旧拾取记录和请求。移交仲裁不重置这些时间或场上道具。生产仍使用现有 sidecar 仲裁随机流，不声称逐位复现 Client.exe 的 RNG。

服务端原来将 0x115A 限于规则 2，现也允许规则 7；保留仲裁检查，并对规则 7 校验 1～3 和真实补给地板坐标。规则 8 等仍拒绝。TCP 副本不重复下发给原生对等客户端。
