# 混合道具栏：房间顺序、紧凑库存与Tab分页

2026-11-04。来源：v848 Client.exe普通汇编、实际执行原版角色构造/初始化和物品发放路径、原版脚本与本地双客户端联调。此前“准备道具按GAME_BEGIN排列、用尽后保留空位”和“没有代码读取Tab”的结论已修正。

## 准备道具从哪里取顺序

地图开局 `0x005B9642` 调用 `InitPlayerProp`。其他玩家及录像模式按GAME_BEGIN前七项；**本机在线玩家走 `0x005B974A`**：

1. 从应用对象 `+0x7D0` 的Section接口虚表 `+0x58` 取房间道具栏的七个ID。
2. 按这七格从左到右遍历，跳过0；在GAME_BEGIN前七项中找相同ID的第一个记录。
3. 创建原版Prop对象、绑定场景及玩家；找不到Prop定义就跳过。
4. 通过 `0x0087EC6D(ID,数量,Tier)` 发放，使用服务器提供的数量，不把房间空格插进战斗库存。

所以房间栏 `[20059,0,20020,20058,0,0,0]`，即使GAME_BEGIN为 `[20020×5,20058×7,20059×9]`，开局也是 **蓝礼花9、药剂5、红礼花7**。原版七格写入函数 `0x005DAC82` 的实际捕获与此相同。

宿主现在将 `GetEquipedProp()` 的七格ID传给sidecar；只改变本机选择/排序，不修改GAME_BEGIN。省略这个字段的旧命令行调用保留按报文排序的兼容行为；显式空栏不会退回报文顺序。PropSet没有定义的旧道具也不会占一格。

## 七格是显示窗口，库存是有序向量

当前属性对象 `P+0x19C` 持有记录大小60字节的原版向量；记录为ID、数量、附加值/Tier三个包装数值。关键路径为：

| 地址 | 行为 |
| --- | --- |
| `0x005A9E83 → 0x005C9A18` | 已有ID在原位置叠加；新ID追加末尾 |
| `0x005A9E9D → 0x005C9D4C` | 扣数；到0后删除记录，后项前移 |
| `0x005AF2D4 → 0x005C9EF1` | 数字键/控制键读取当前格ID |
| `0x005C9FFC` | 取数量 |

没有七种物品的物理容量上限，也没有255个的数量上限。准备道具和拾取道具按实际发放时序共用这一向量。如果先发一个场景道具，再初始化准备道具，它保留在最前面；消耗完再捡到同种物品，会重新追加到末尾。

独立原生输出：

```text
初始：20059×9, 20020×5, 20058×7
再发41,42,43,44,45,46,63,64,65各1：共12种，全部保留
药剂用尽：20059×9, 20058×7, 41,42,43,44,45,46,63,64,65
41再加255：数量256
先发41再装准备道具：41,20059,20020,20058
41用尽后重拾：20059,20020,20058,41
```

引擎新增默认关闭的 `NativeActionInventory`，原生客户端联网/练习启用，记录完整顺序及32位数量。原有策略/训练的固定七格观察、字节数量投影与默认有界模式保留；游戏侧的所有权、消费、阵亡掉落、清空、复活及Clone使用完整库存。实例序号只用于区分“一次宿主step内用尽又重拾”的新旧堆叠，不出现在游戏网络协议中。

sidecar按发放时序合并本机准备道具与完整拾取库存，输出 `slots`；数量归零就移除，宿主直接显示对应七格窗口。冷却始终按当前显示的ID/Tier查，不因前移/翻页错位。

## Tab确有路径，但原版分页有缺陷

`0x006101DF` 构造的组件被普通规则及特殊规则注册；更新 `0x0061021C` 调用 `0x005A4C2B`，读键盘状态 `+0x22 = +0xC + 22`。第22项默认DirectInput扫描码0x0F，即Tab；聊天框打开时跳过本机输入。

Tab调用 `0x005C9EC9`，将页偏移加7，越界回0。然而 `0x005C9EF1/0x005C9FFC` **只在边界检查中加了偏移，实际读取仍用原下标**。没有看到这个组件同步刷新道具栏。并非没有Tab分派，也不是切选中格。

原生实测：上面的11项库存按Tab后偏移7，读取0～6得到 `[20059,20058,41,42,0,0,0]`，而不是后面那页。这是明确的漏偏移问题。按项目既定的“修明显原版bug”约定，宿主实现完整分页：**Tab切换七格页，图标/数字键/Ctrl统一使用当前页，Ctrl仍只扫描页内0～5格**；没有选中框。库存缩到一页时自动回第一页。
