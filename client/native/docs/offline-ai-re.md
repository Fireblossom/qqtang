# 离线对战（全部玩法 + 电脑对手/队友）

更新于 2026-11-18。目标：不连服务端，在 Mac 客户端里和电脑对手、电脑队友打每一种玩法。这是**宿主新增功能**，原版没有；规则部分仍是原版规则（全部复用联网模式已核对过的代码）。

## 1. 设计：每个座位一个客户端，本机做仲裁方

离线模式不是另写一套规则，而是把联网对局原样跑在进程内：

- 规则辅助进程（`cmd/qqt-battle-sidecar`）收到 `{"cmd":"init","offline":{...}}` 后，按服务端的做法合成 GAME_BEGIN（`offline.go` 的 `offlineCompetitiveBegin`，等同 probe `newCompetitiveGameData`：地图道具池 + 规则目标物品 `CompetitiveObjectiveSceneItems` + 小鸟延时补给 `PlanCompetitiveSupply`；探险关卡用 `configs/adventure-rules.json`，等同 `newAdventureGameData`）。
- **每个座位建一个 `onlineMatch`**（联网模式用的同一个对象）：本机玩家那一个是仲裁方，和“房间里只有自己 + 服务端 AI”时一样；每个电脑座位是一个普通的非仲裁客户端，它的本地玩家由策略（自动机器人或 rule-1 模型）代替键盘操作。所以电脑座位自己检测被炸（0x0FA5）、阵亡（0x0FA7），向仲裁方请求拾取、推箱、踢泡、拿包子/放包子（0x0FB6/0x0FB8）、雕像碎片、机器发射、箱子推动……全部走联网时真人用的路径，不需要替它们伪造任何“请求结果”。
- `offlineHub` 代替网络和服务端：
  - **UDP**：各客户端的 Type-2 组播按目标列表原样交给目标客户端（与服务端 QQTPPP 中继转发同样的字节，`route`）。`onlineMatch` 只多了三处 `offline != nil` 分支：不开套接字、不做登记/握手、发送改交给 hub。
  - **时钟**：所有客户端共用 hub 的场景时钟，每个 step 命令推进 `ticks×20 ms`（与练习模式一样由客户端的帧推进，暂停、无界面快跑都不受墙钟影响）；客户端标签 `clientTag` 加 0～19 ms 抖动，因为原版帧时间不落在 20 ms 上（箱子发射器用它的最低位选方向）。
  - **TCP（REQUEST_PLAY 镜像）**：交给 `offlineReferee`，它照 probe `game_event_dispatch.go`/`competitive_death_dispatch.go` 的方式喂服务端自己的账本 `internal/game/match.CompetitiveBattle`（击杀、救人、阵亡、复活、包子/雕像、夺宝宝石、糖客基地血量、机器/箱子耐久、Boss 死亡、箱子 NPC 登记）。服务端要回的几种也在这里回：0x0FAF→全员 0x0FB0（道具使用）、0x1174→0x1175（带入道具）、箱子 NPC 的 CREATE_NPC_BOSS 回显、开局 50 ms 的 CREATE_NPC_BOSS（Boss 叠加层）和 CREATE_PVENPC_BOSS（探险掉落表）、REQUEST_GAME_NEXTMAP（探险过关）。
  - **结束**：账本判出胜负后，按服务端的 750 ms（Boss 胜利 10 s）延迟生成 GAME_OVER；时间到用 `ConcludeTimeout`。GAME_OVER 的形状与 probe `competitiveGameOverData` 一样（杀敌/救人/奖励三组计数与得分、胜 50/平 20/负 10 基础分），客户端用联网的 `result_rows` 和结算画面显示。离线不存任何积分。
- 机器规则的招式（0x115C/0x115B，`machine_skill.go`）本来就是客户端之间直接收发，离线照常可用（本机玩家可以出招，电脑不会出招）。

为什么不在一个引擎里直接“替电脑造请求”：联网代码到处以“本机玩家/远端玩家”区分（119 处 `match.local`），把它改成多本地玩家要动每个规则文件；每座位一个客户端则一行规则代码都不用改，联网里已经实测过的仲裁/非仲裁两条路径都被复用。代价是 N 个引擎同时运行：2 对 2 一局 4 分钟在无界面测试里约 3 秒，界面里无感。

没有改 `internal/game/battleengine`。

## 2. 电脑的策略

- **规则 1、4（普通、比武）**：默认用 rule-1 ONNX 模型 U2392（`configs/models/qqtang-rule1.onnx`，`offline_policy.go`），与服务端部署一致：每座位一份带循环记忆的策略、按元数据 MinP 0.1/温度 1 采样、每座位独立随机流、每 100 ms 决策一次并保持方向键、放泡/道具只在决策那一拍发（probe `competitiveAIDecisionCadencePolicy`）。需要 `-tags onnxruntime` 编译和 ONNX Runtime 1.29 库；没有时自动退回机器人。有 Boss 的地图不用模型。
- **其他规则（以及没有模型时）**：自动机器人 `autoplay.go`（原来给双客户端测试用的那个）加上离线专用的改进（`autoplay_offline.go`，只在 `bot.offline` 时生效，测试机器人行为不变）：
  - 逃生按“身体先进下一格”计时（strict）：只有最后一波爆炸已过的格子才会穿过；找不到安全路线才退回原来的宽松估计。旧算法在“下一格的爆炸会在我走满一格之前结束”时会直接走进去，自杀主要来自这里。
  - 泡一放、一动或一炸，立即重算危险表（原来最多晚 100 ms）。
  - 放泡前检查队友：会炸到被困的队友就不放；炸到能走开的队友照放（队友会躲）。
  - 被困的人：走过去碰——对手就击杀，队友就救出（12 格内）。
  - 糖客战：优先去能让爆炸穿过敌方基地中心的位置放泡。
  - 被可推的箱子围住（311 开局每人都在箱子圈里）时把箱子推开；没事可做时朝对手走。
  - 站在格子边缘时先对正再决定，避免在两个格子之间来回抖（两名队友互相挡住时出现过）；在“好位置”放不了泡最多等 1.5 秒，然后 5 秒内不再选这个格子。
- 所有电脑座位都是“对手”或“队友”，取决于队伍号；队伍号由房间或命令行决定。

## 3. 入口

- **界面：新手练习 → 自由练习 → 练习房间**。原版自由练习直接在 311 开一局（`tutorial-re.md`）。现在改为打开**原版房间界面**的离线练习房间：座位 1 是自己（房主），座位 2 是一个电脑对手，地图默认 311，点“开始”就是原来的 311 自由练习。在房间里可以：
  - 用原版“选择地图”对话框选任何模式和地图（推箱子、机械世界、夺宝、英雄、足球、抢包山、糖客战、比武、普通、探险……），原版的 5 秒开始锁、积分门槛照旧；“选择模式”切竞技/道具/探险；房间属性里的自由模式生效；
  - 换自己的角色和队伍颜色；
  - 点空座位加一个电脑对手（队伍 2）；点电脑座位换它的队伍：2→3→4→1（成为队友）→移走；
  - 开始后对战结束（或点离开）回到练习房间，点“返回”回大厅。
  - 房间的原生函数在 `room.py` 里本地应答（`state.offline`），不向服务端发任何房间请求，房间里走动的 UDP 也不发。
  - 选这个方案而不是另做界面：房间、地图对话框、角色和队伍选择都是原版界面，只是“服务端”换成本地；原版自由练习按钮打印的就是 `enter freePractice room`。代价：自由练习多了一步“开始”。设环境变量 `QQT_DIRECT_FREE_PRACTICE=1` 可恢复原来的直接开局。
- **命令行**：`--practice MAP` 现在走离线模式，支持任何地图（含探险关卡）：

  ```sh
  .venv/bin/python -m qqtclient --client-root <客户端目录> --practice 801 --teammates 1 --opponents 2
  .venv/bin/python -m qqtclient --client-root <客户端目录> --practice 1003 --teams 1,1,2,2 --policy onnx
  .venv/bin/python -m qqtclient --client-root <客户端目录> --practice 11 --teams 1,1      # 水手 Boss，两人合作
  .venv/bin/python -m qqtclient --client-root <客户端目录> --practice 1601 --teams 1,1 --level 3000   # 探险路线
  ```

  `--teams` 按座位给队伍号（自己第一个）；`--boss` 打开地图的 Boss（11、124 总有）；`--policy auto|bot|onnx`；`--free-rule`；`--autoplay` 让本机座位也由电脑操作（截图和测试用）。结束后回车再来一局、Esc 退出。
- 编译：`tools/build-sidecar.sh` 在 macOS 上找到 ONNX Runtime 库（`QQT_ONNXRUNTIME_LIB`，或发布包 `runtime/onnxruntime/darwin-arm64/libonnxruntime.1.29.0.dylib`，含 `~/Downloads/QQTang-Local-v1.3.4/QQTang-Local/…`）时用 `CGO_ENABLED=1 -tags onnxruntime` 编译，并把库、模型、`configs/adventure-rules.json` 的路径写进程序作默认值；`QQT_SIDECAR_ONNX=0` 关闭。默认编译（无 cgo）照常可用，电脑全部用机器人。运行时也可用 `QQT_ONNX_MODEL`、`QQT_ONNXRUNTIME_LIB`、`QQT_ADVENTURE_RULES` 指定。

## 6. 已知差别和缺口

- **仲裁方的时间优势**：本机是仲裁方，拿包子/拾取由本地引擎立即裁定，电脑的请求要隔一拍才到。抢包子里本机所在队明显占优（机器人对机器人的一组 10 局对比：仲裁方所在队 10:0，把仲裁方换到另一队后仍是仲裁方所在队 10:0；20 局轮换地图 14:6）。这与原版房主做仲裁方时的不对称是同一性质，没有消除。
- 机器人只做了基本战术：不会主动设陷阱围人，踢炸弹玩法里很少踢中人；比武/夺宝时间到前很少分出胜负。
- 离线 Boss 不掉奖励物品（奖励表在服务端配置里）；AIType 5（踢炸弹 Boss）和海盗解释器本来就没做。
- 结算显示的积分按服务端公式计算，但不保存。
- 练习房间里自己的服装（2026-11-19 补上，宿主新增）：在线房间里座位记录的物品是服务端复制的登录物品（`enter_room.go` `PlayerInfoInRoomOldFromProfile` 用 `ToClientLoginConfig().Items`），练习房间没有服务端，所以改用登录资料 `session.profile.items`（商城的物品更新会改它）；没有登录资料时（如断线后）用本地缓存：进分区、进在线房间、开练习房间时，把角色字节非 0 的物品（`room_changePlayer` 只穿角色字节等于当前角色的物品）按号码存进 `state.json` 的 `practice_wear`。都没有时不穿。测试：`tests/test_offline.py` `PracticeWearTest`。
- 练习房间：没有踢人/锁座位（点锁住的座位会打开它）；房间聊天只在本地显示。
- 探险关卡时间到的处理是宿主决定；探险勇气值按服务端公式累计，未乘胜负倍率。
- 电脑不会用道具场带入道具，也不会出机器招式。
