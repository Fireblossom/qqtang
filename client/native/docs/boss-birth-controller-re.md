# Boss出生状态：默认控制器恢复路径

2026-11-04，v848。原先“水手32、35/36可能永久停在模式9”的疑点已定位到默认状态控制器；不能把 `0x005AE672` 没有写模式1理解成永久无敌。默认控制器现已接入宿主，并在Ready期间更新；旧1000ms年龄门控已删除。默认图片路径后续按完整构造/绘制证据修正：birth槽未自动加载，保留阴影与血条，见 `npc-picture-re.md`。

## 真实角色帧执行

工具 `tools/probe_boss_birth.py` 执行实际状态控制器构造 `0x005C06C9`、出生设置 `0x005ACBFC` 和NPC虚表+30的 `0x005ABE96`。场景中的仲裁方比较按输入设置；控制器、模式查询、停止检查、站立进入回调和角色模式写入均运行原函数，没有替换成宿主状态机。

默认状态由 `0x005C06EB` 返回，虚表 `0x007A2080`：+30 `0x005C0C9B` 返回3000，+34返回状态2。`0x005C0743` 先比较旧计数，旧计数小于3000才加本帧dt，否则调用完成回调 `0x005C0C83→0x005C07D6`；成功后计数归0，并经+8 `0x005C0C8F→0x005AC934` 设置 `Actor+3B7=1`、`+3B8=1`。

因此20ms输入下，3000ms时仍为模式9，3020ms那次角色更新才恢复1；17ms下旧计数先到3009，3026ms那次恢复。不能简单改成 `age>=3000` 就宣称逐帧等价。

| 角色 / 观察方 | 无附加特效时首次模式1（dt20） |
| --- | ---: |
| 32、35、36，仲裁方 | 3020ms |
| 32、35、36，非仲裁方 | 3020ms |
| 24、28、34，仲裁方 | 20ms（第一次角色帧） |
| 24、28、34，非仲裁方 | 3020ms |

24/28/34的仲裁角色帧会先经过 `0x005AE672` 台词分支，直接写模式1，再尝试停止，所以不必等默认计数满。其他角色的仲裁方只把+3CC置-5001；非仲裁方在本探针完整帧路径中+3CC仍为1000，没有按1000ms自行递减。

## 特效完成是独立门控

`0x005C0774` 还检查 `Actor+3E8` 指向对象的虚表+C是否完成，`0x005AC934` 再检查一次。对象为空或完成时恢复；持续未完成时，控制计数卡在3000，模式9保持到观察结束4200ms。若完成输入在3100ms变为真，则当次更新恢复，计数不重走三秒。

这只是附加对象完成谓词的控制输入，不把它称为已经还原出生图、特效内容或图形资源的真实完成周期。台词角色仲裁分支直接写模式1，在“附加对象一直忙”输入下亦会写1，但其控制器停止仍受门控。

## 记录、依赖和生产边界

`boss_birth_v848.jsonl` 共68条序列、15496个角色帧：角色24/28/32/34/35/36、两种仲裁身份、17/20ms、空/已完成/一直忙/3100ms完成的附加对象。24/28只记录默认20ms的空对象。记录列为 `[elapsed, actorMode, walk, controllerCounter, controllerMode, greetingTimer]`。

NPC分类、台词文字及台词发送/通知入口为受控依赖；没有执行TCP/UDP、完整Actor图形构造、远端移动组件或整个场景调度。全部控制序列可重新生成；生产使用的 `bossBirthState.frame` 现已逐项对照68条序列、15496帧的模式、walk、计数与台词计时字段。

修正前，宿主 `sceneClock()` 在Ready期间最低返回3000，Boss创建时的 `bornAt` 取引擎时钟，再等待1000ms；这样把创建时刻和Ready期混在了一起。修正后保留引擎现有时钟约定，出生另用从场景开始累计的角色帧时间：创建读取上一角色帧时间，本次先处理命令，末尾再推进角色帧，即使引擎仍停在3000也更新。AI只在开局时间严格大于3000且上一角色帧已经恢复模式时执行；受伤许可亦看出生模式，受击闪光保护仍独立。

该原版路径足以排除“仅因台词分支没写1便永久卡住”的解释；完整Windows场景中是否有其他保护区入口提前改变状态，仍不在本隔离执行的覆盖范围内。
