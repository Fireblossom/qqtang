# 机器本体、就绪图与入口箭头的动画时钟

2026-11-04。来源：v848 Client.exe更新/绘制/图片推进函数的实际执行和原版DIMG。实现位于 `battle/machine_projectile.py` 的 `MachineGateAnimation`，继承已核对的两段发射物。历史录像和Windows完整启动流程的逐帧对照仍未完成。

## 元件和时间单位

原版 `0x005EF47A` 为每台机器创建独立图片对象：

| 元件 | 首侧 / 另一侧 | 帧数 |
| --- | --- | ---: |
| 冷却本体 | misc163 / misc164 | 8 |
| 就绪本体 | misc401 / misc402 | 12 |
| 发射本体 | misc167 / misc168 | 24 |
| 本机入口箭头 | misc400 | 2 |

图片数据构造 `0x00487360` 给出300ms周期，循环开启。更新 `0x0042A680` 累加传入时间，整除周期推进帧，保留余数；跨过帧数上界时直接回0，不保留跨越的多余帧。发射图的stand/trigger文件在此原包中相同。

本轮另外核对调用链，避免只看默认周期猜最终速度：`0x005B8009` 把同一dt加到 `M+0x3838` 场景时间，并交给三个地图层的 `0x005D8A77`；后者原样传给元素虚表 `+0x1C`，没有额外三倍换算。宿主因此用场景时间增量推进本体/箭头；发射物仍按原版每次回调固定1/2像素推进。

## 更新顺序与暂停

机器更新 `0x005EF7DE` 按以下顺序：

1. 上一帧本机箭头可见，先更新箭头dt。
2. 上一帧处于就绪，更新就绪图dt；否则仅在上一帧绘制时钟距发射已过800ms（或从未发射）时更新冷却图dt。
3. 重新计算当前冷却就绪状态与入口通行位，确定本机箭头可见性。
4. 写入当前绘制时钟。发射后不足800ms时压掉箭头，更新发射图 **3×dt**。
5. 更新两段发射物。第二段推进时，原版 `0x005EF912` 把元素 `+0x64` 的绘制时钟缓存写成1；该字段不是 `M+0x3838` 的场景时间。

隐藏元件暂停推进，保留各自帧/余数。发射函数 `0x005EFB2D` 选择发射图的trigger动作；`0x0042A7E0` 不清空当前帧或余数，所以之后的发射**接着上次相位**。不能用“全局场景时间除100”选帧，也不能每次发射都从0开始。

绘制 `0x005EF91F` 依次处理就绪/冷却本体、800ms内发射图、两段发射物、本机箭头。更新使用上一帧状态，绘制使用新状态，因此存在真实边界：恰到就绪时已画就绪图0帧，冷却图刚最后推进一次；发射窗口刚结束时已画冷却图，但这一帧尚未恢复冷却图计时。

## 原生函数基准

`tools/probe_machine_animation.py` 执行真实机器构造、`0x005EF7DE` 更新、`0x005EF91F` 绘制、冷却判断，以及真实图片数据构造/推进/动作选择。图形设备调用仅被观测，DIMG帧数来自原版文件。两个投射物仍使用真实构造、路径设置及运动函数。未改原版文件。

```sh
.venv/bin/python tools/probe_machine_animation.py /path/to/client-patched
```

20个独立检查点保存在 `tests/fixtures/machine_animation_v848.jsonl`。测试逐帧模拟从3000ms开始的20ms更新、两次发射及长帧，再比较各元件帧/余数、绘制顺序、箭头、就绪位和绘制时钟；不是从移植生成期望值。代表性原生输出：

| 场景时间 / 事件 | 关键结果 |
| --- | --- |
| 48000，首次就绪 | 冷却图6帧余20；已显示就绪图0帧和箭头0帧 |
| 48420，启动发射 | 就绪图/箭头最后加20ms，然后发射图0帧余60 |
| 49200，启动后780ms | 发射图8帧余0；冷却图仍暂停在6帧余20 |
| 49220，启动后800ms | 已画冷却图，所有图片本帧都没有推进 |
| 49240 | 冷却图恢复，6帧余40 |
| 96840，第二次发射 | 发射图接在8帧余60 |
| 长dt导致就绪帧号越界 | 回0，保留时间余数；不按帧数取模保留多余帧 |

时钟和dt可独立控制；这些是给定初始化和更新序列的元件基准，不代表Windows完整Ready/Go首帧的相位已经录像验收。
