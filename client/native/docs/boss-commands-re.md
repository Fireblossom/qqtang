# 通用Boss路径消费与场景命令顺序

2026-11-04，接续 `boss-motion-re.md`。AIType3现在使用共用原版路径消费、追加逃生向量、节点kind标记与场景移动命令；不再用“按当前格丢节点”的替代逻辑或每Boss独立的决策计数。

## 路径与节点

原版 `0x005B1EA6` 是通用Boss `0x005DF058` 与漫游NPC `0x005DEF29` 共用的函数。已对照的 `npcPathFollower` 现也通过Boss桥接使用：保留float32位置和Actor+7AC失配计数，处理少于两节点清空、十次失配后吸到格心、格心±10px窗口、按档位/dt前探、用当前朝向查询通行和站立分支。格心弹出节点返回1，即使仍有后续节点也进入本次fallback，保留该行为。

Boss桥接逐项通过既有47条真实 `0x005B1EA6` 基准：位置、节点序列、失配计数、返回值及完整通行查询参数均一致。它们复用于Boss接入验证，不额外加入记录总数。正式调用仍以一个20ms引擎tick对应一个决策帧。

路径节点的第4偏移字节（六字节节点的byte4）同时保存类型/放泡标记，Go对应 `kind`；byte5是填充。原Go字段 `marker` 实际映射填充，现更名为 `padding`。`0x005DF0EB` 读取的是byte4，故放泡资格统一使用已经对照30组输入的 `npcBubbleEligible`；寻路写入当前节点时kind先置0，箱子截断时置4，追击目标最远节点也在kind写4。填充为4不会触发放泡。

`0x005B0598` 找到逃生路线后会追加到已有原生vector末端，反转为Go的start..goal顺序就是把新逃生路线放在旧路线之前。通用Boss现复用 `appendEscape`，实际非空vector基准也经Boss桥接比较，不再直接替换旧路线。

## 移动与放泡命令

规则1实际构造/注册的命令顺序是移动 `0x006112AF` 在放泡 `0x00610BA0` 之前，见 `npc-rule-dispatch-re.md`。原始 `rule_dispatch_v848.jsonl` 的6组规则1轨迹（3个受控默认NPC角色×40/200帧）现逐项比较Go组合入口，方向决策与每帧放泡回调的顺序完全一致；这验证共用命令层，不把受控AI回调冒称为Boss完整规划器对照。

移动计数器属于场景命令对象，不是AI对象。`bossRule.moveCommand` 现在保存该计数，复用已对照416项的 `npcMoveCommand`；方向非9才清零，返回9时下一帧重试。放泡规划不访问此计数，不会因为放了一颗泡而重新推迟下一次移动决策。

实际组合次序为：场景移动命令决定是否调用AI → 应用新行走/停止命令 → 放泡检查/规划 → 世界物理。无新方向时持续使用已有命令。真实宿主回归另验证kind4/填充4的差别、放泡后场景计数保持，以及首颗泡真实爆炸后的逃生。

相关侧车、引擎、协议全套测试与Mac、Windows/386构建通过。复用的是已有原版记录，累计仍为7526条，不因桥接回放重复加总。

AI整体的目标选择/随机状态、危险规划与完整世界调度仍需继续核对；探险及特殊控制器仍有独立兼容路径。本轮没有把共用函数与命令层对照扩展成整个Boss AI或源Win32整局等价结论。
