## 1. 通用基类 CMapElement

构造 `0x005EEC60`，虚表 `0x007A369C`。工厂由 `FUN_005f528a(类名, 大小, 创建, 销毁)` 注册，元素 ID → 类名表在 `0x007A3848`（`0x005F532D` → `0x005F52EA`）。[证实]

### 1.1 字段 [证实偏移；含义多数证实]

| 偏移 | 含义 |
|---|---|
| `+0x04` | 元素 ID |
| `+0x08` / `+0x0A` | `short row` / `short col`（绘制用 `col*40`、`row*40`，边界检查 row 0..12、col 0..14） |
| `+0x0C` | 状态：1 正常，2 正在消失，3 被推动中，4（另有用途） |
| `+0x10` | 剩余耐久 = 属性 `+0x0C`（[推断] 就是 mapElem.py 的 `LifeTime`：`vtbl+0x34`=`0x005EF264` 以 `LifeTime ≥ 0` 判断可否破坏，坚石取 3 正好对应三击） |
| `+0x14` | 属性对象（`0x005C3B44(id)`）：`+4/+6` 尺寸宽/高（格），`+8/+0xA` offset，`+0x0C` LifeTime，`+0x14` 标志（`&2` canMove，`&0x10` 用于 `vtbl+0x24(6)`），`+0x18` GridAttr 数组 |
| `+0x1C` | 所在图层管理器；`+0x1C→+0x34` 是游戏对象 M（`M+0x3828` 本机玩家，`M+0x3838` 游戏时间 ms，`M+0x3824 == M+0x3830` 表示本机是仲裁方） |
| `+0x20` | 正常动画；`+0x24` 消失动画；`+0x28` 消失倒计时 |
| `+0x30` / `+0x34` | 顶层管理器 `M+0xE2C` / "本元素在墙层 `M+0xE78`"（绘制时若顶层同格有别的元素，墙层元素不画）|

三个图层：`M+0xE2C`（顶）、`M+0xE78`（墙）、`M+0xEC4`（地面）。从 S 访问时是 `S+0x213C/0x2188/0x21D4`（`S+0x1310 = M`）。[证实]

### 1.2 虚表槽 [证实]

| 槽 | 基类实现 | 作用 |
|---|---|---|
| `+0x04` | `0x005EEE22` | 初始化：取属性对象，`+0x10 = LifeTime`，调 `+0x3C` |
| `+0x0C` | `0x005EF003` | 绘制：状态 1/3 画 `+0x20`，状态 2 画 `+0x24` |
| `+0x1C` | `0x005EEE71` | 每帧更新(dt) |
| `+0x2C` | `0x005EF1AA` | 玩家能否从方向 d 进入：GridAttr 低 4 位，方向 0→bit 8，1→4，2→2，3→1（`|0x80` 的变体另有映射；4/0x84 → 任一位） |
| `+0x30` | `0x005EF20F` | 火焰方向：0→0x800，1→0x400，2→0x200，3→0x100（[推断] 是"火焰穿越"位，与 mapElem.py 注释"玩家穿越，遮蔽玩家，火焰穿越，遮蔽火焰"四个半字节一致）|
| `+0x34` | `0x005EF264` | 可破坏：`LifeTime ≥ 0` |
| `+0x3C` | `0x005EF283` | 进入正常态：`+0xC = 1`，加载动画 `0x05000001 | (id/1000)<<16 | (id%1000 & 0xFF)<<8`（stand） |
| `+0x40` | `0x005EF2CF` | 消失：`+0xC = 2`，`+0x28 = 500`，加载动作 6（die） |
| `+0x48` | `0x005EF322` | 事件处理 `(code, arg)`：`code == 1`、状态不是 2、可破坏 → `+0x40` |
| `+0x4C` | — | 只在 Totem/Halo 子类里有，见下 |

### 1.3 消失流程 [证实]

`+0x40` 之后：每帧更新里状态 2 推进 `+0x24` 动画（播完就释放），`+0x28 -= dt`；`+0x28 < 1` 时如果该格仍是自己，就从格子移除（`0x005D855A`）。因此**元素在 500 ms 内仍占格**：通行判断 `0x005EF1AA` 只看 GridAttr、不看状态，所以这 500 ms 里照样挡人、挡火 [证实：代码无状态判断]。

素材：`common/elem18/19/21/24/25/27/28_stand.img` 存在，**没有任何 `_die.img`**（只有 `common/elem21_trigger.img`，代码里没看到用它），所以这几种石头被打掉时 die 动画加载失败、500 ms 内什么都不画（只有子类自己的特效）[推断：加载失败返回 0，绘制前都判空]。

### 1.4 正常贴图位置 [证实公式]

状态 1：`x = col*40 − offset.x + 8`，`y = row*40 − offset.y + 21`（`0x005EEE71`，offset 取属性对象 `+8/+0xA`，[推断] 即 mapElem.py 的 `offset`）。

## 2. 事件来源和网络消息

### 2.1 元素事件码 `vtbl+0x48(code, arg)` [证实]

| code | 来源 | arg |
|---|---|---|
| 1 | 被炸：泡泡爆炸 `0x005FAFB5` 对火焰覆盖的每格的三层都发；`0x005D8E20(2,…)` 的 3×3 爆炸也发 | 0 |
| 4 | 本机玩家移动中进入新格（组件 `0x0060D2CD`），发给新格三层的元素 | 玩家 |
| 6 | 同一组件，每帧发给玩家所在格三层的元素 | 玩家 |
| 7 | 同一组件：玩家**没换格**、正在移动（`+0x3B8 == 2`），朝向 `+0x3B4`（0 右 col+1，1 上 row−1，2 左 col−1，3 下 row+1）的相邻格有任一层 `vtbl+0x2C` 返回"不可进入" → 给相邻格三层元素发 7，即"顶着它走" | 玩家 |
| 8 / 9 | 光环请求 / 光环生效（0x1176 收到后分派） | 玩家 |
| 10 | 收到 0x1176 type 10 时（非仲裁方）也会分派到元素，元素都不处理 | 玩家 |
| 0xF | 图腾计时到期（本地） | — |
| 0x10 | 图腾激活（仲裁方本地 + 收到 0x1176 type 0x10） | 玩家 |
| 3 | 猪窝自己发 | 0 |

组件 `0x0060D2CD`（构造 `0x0060D290`）和其他角色组件一样，**每帧只对本机玩家调用**（仲裁方再对 NPC 调用）[证实，引用 `adventure-combat-re.md` §1.2]。玩家坐标：`A+0x338/0x33C` 当前 x/y，`A+0x3A8/0x3AC` 上一帧 x/y，格 = `int(坐标)/40`。

### 2.2 场景动作 `0x005D8E20(kind, elem, arg)` [证实汇编]

- `kind 2`：`r = *arg`（这些元素都传 1），对 `elem` 周围 `[row−r, row+r] × [col−r, col+r]` 的每格、三层元素依次发事件 1（`0x005D8D93`）。**同步执行**，所以会在同一帧内连锁。只碰地图元素，不碰泡、不碰玩家、不碰地上道具 [证实：只调 `0x005D8D93`]。
- `kind 10`：`arg` 是玩家。
  - 本机不是仲裁方：发 0x1176 `{type=10, id=玩家+0x328, time, row, col, row, col}`（TCP `0x005A1DE1` + 组播 `0x005A2F4C`，不本地分发）。
  - 本机是仲裁方：直接组 **0xFA7（ID_NOTIFY_PLAYER_DIE）**，带掉落道具（规则对象 `+0x4EA4` 的 `vtbl+0x18` 取要掉的道具，`0x005B8574` 在全图随机选格，最多 64 个），TCP + 组播 + 本地分发。格式同 `adventure-combat-re.md` §4.1：`{u16 id, u32 time, u16 x, u16 y, u8 n, n×{u32 item, u8 row, u8 col}}`。
- `kind 0xB/0xC/0xD/0xE`：传送门相关，不在本文范围。

### 2.3 0x1176 地图元素消息 [证实]

16 字节：

```
u16 type      // 8 光环请求, 9 光环生效, 10 请求杀人, 0x10 图腾激活（0xD/0xE 是传送门）
u16 playerId  // 玩家 +0x328（图腾激活时填仲裁方本机玩家，无意义）
u32 time      // M+0x3838
u16 row, col  // 元素格
u16 row2, col2// 目标格；本文所有类型里都等于元素格
```

接收 `0x005FD4E6`：`player = 0x005A287F(playerId)`；
- `type == 10` 且本机是仲裁方（`S+0x4B34 == S+0x4B40`）→ 给 `player` 组 0xFA7（与 2.2 相同），**不校验位置**。
- 否则 → 对 `(row2, col2)` 的三层元素调 `vtbl+0x48(type, player)`。

## 3. 各元素

### 3.1 CMEExplodeStone 爆炸石（17019）

注册 `0x00619CE0`，构造 `0x00619D6D`，虚表 `0x007A4E64`，大小 0x3C。

- 初始化 `0x00619DF5`：`+0x38 = effect/Totem_Flame.eff`（借用火图腾的特效）。[证实]
- 事件 `0x00619E81`：`code == 1` 且状态不是 2 → `+0x40`。**不看 LifeTime**（LifeTime=1 本来也是一击）。[证实]
- 消失 `0x00619E96`（状态不是 2 时）[证实]：
  1. 基类消失（状态 2，500 ms）。
  2. 特效从头开始，并立即快进 400 ms（`0x00582CF0` 清零、`0x00582D20(400)`）。
  3. `0x005D8E20(2, this, &1)`：3×3 地图元素被炸 → 箱子破坏、坚石掉一点耐久、冰石碎、相邻爆炸石**连锁**（递归回到自己时因状态 2 被忽略）。
  4. 杀人检查 `0x00619EE1`。
- 每帧更新 `0x00619E15`：基类更新；状态 2 时推进特效、再做一次杀人检查。所以**杀人判定持续到元素被移除，约 500 ms**。[证实；"移除后不再更新"为推断]
- 杀人检查 `0x00619EE1`：本机玩家 `A = M+0x3828`；`A+0x3B7 != 4`（4 = 垂死/死亡，[推断]）且 `|row(A) − row| ≤ 1`、`|col(A) − col| ≤ 1` → `0x005D8E20(10, this, A)`，即死亡（0xFA7），不是困泡。每帧都会发，直到本机状态变成 4。[证实；"直到状态变成 4"为推断]
- 绘制 `0x00619E42`：状态 2 时把特效画在 `(col*40 + 26, row*40 + 40)`，再画基类。[证实]
- 特效 `Totem_Flame.eff`：图 `magic131`（`object/magic/magic0131.img`），100 ms/帧，关键帧 0～1195 ms [证实数据]。

### 3.2 CMESolidStone 坚石（17021）

注册 `0x00619F6A`，构造 `0x00619FF7`，虚表 `0x007A4EB0`，大小 0x38。

- 事件 `0x0061A038`：`code == 1` 且状态不是 2 → `+0x40` = `0x0061A04D`。[证实]
- `0x0061A04D`：[证实]
  - `life < 2` → 基类消失（500 ms 后移除）。
  - 否则 `life -= 1`，丢掉正常动画，换成 `effect/default_MapElement.eff` 上挂图 `effect/Stone_Life%d.img`（`%d` = 新的 life），先放在格心 `(col*40+20, row*40+20)`；之后每帧基类更新把它移到 1.4 节的正常贴图位置。
- 结论：LifeTime 3 → 第 1 击显示 `Stone_Life2.img`，第 2 击 `Stone_Life1.img`，第 3 击消失。每次爆炸对同一格只发一次事件 1，同一帧多个泡炸到同一格算几次取决于爆炸处理 [未知]。
- 素材 `effect/Stone_Life1.img`、`Stone_Life2.img` 在磁盘上 [证实]。

### 3.3 CMEIceStone 冰石（17018）

注册 `0x0061A0EE`，构造 `0x0061A17B`，虚表 `0x007A4EFC`，大小 0x3C。没有地图用到。

- 初始化 `0x0061A203`：`+0x38 = effect/Stone_Ice.eff`（磁盘和 object.pkg 里都没有这个文件，[推断] 不显示）。
- 事件 `0x0061A313`：`code == 1` 且状态不是 2 → 消失 `0x0061A328`。
- 消失 `0x0061A328`：重置特效；本机玩家在 3×3 内 → 挂减速；然后基类消失。
- 更新 `0x0061A223`：状态 2 时推进特效，并每帧再判一次 3×3 → 挂减速。
- 减速：`A+0x6D8 = 15000`，`A+0x6DC = −3`，`A->0x005ADF32(0x005DB31D(A, 5))`：建 5 号移动状态（构造 `0x005DB65F`，虚表 `0x007A34DC`），放到 `A+0x3E8`，**替换**原来的移动状态（不叠加，见 `boss-ai-re.md` §7.3）。[证实]
  - `+4` 每帧 `0x005DB6E0`：剩余 15000 −= dt，小于 0 时解除。
  - `+8` 速度档 `0x005DB6B9`：`v = 正常速度(0x005AA06B) + (−3)`；`2 ≤ v ≤ 10` 时返回 v，否则返回 2。
  - `+0xC` 返回 0，`+0x10`、`+0x14` 返回 1（与减速胶 1 号的 1/1/1 相比，`+0xC` 不同，含义 [未知]）。
  - 由于消失期间每帧都会重新挂，实际持续时间约为"最后一次在范围内的那帧 + 15000 ms"。不检查玩家状态。
- 绘制 `0x0061A2CF`：状态 2 时特效画在格心 `(col*40+20, row*40+20)`。

### 3.4 CMETotem 基类（图腾）

构造 `0x0061AA52`，虚表 `0x007A4FE4`（基类本身不在元素表里）。

字段 [证实]：`+0x38` 激活剩余（1000），`+0x3C` 周期计时（4000），`+0x40` 图腾状态（6 待机，7 激活），`+0x44` 特效。

- 更新 `0x0061AAF4(dt)`：[证实]
  ```
  if st == 7:
      active -= dt
      if active < 1: st = 6
      else: this->vtbl+0x4C()        // 激活期间每帧施加效果
      特效推进 dt
  timer -= dt
  if timer < 1: this->vtbl+0x48(0xF, 0)
  基类更新
  ```
- 事件 `0x0061AB88`：[证实]
  - `0xF`：`st != 7` 且本机是仲裁方 → 发 0x1176 `{type=0x10, id, time, row, col, row, col}`（TCP + 组播），再本地 `vtbl+0x48(0x10, 0)`。非仲裁方什么都不做，于是计时停在 <1，每帧调一次 0xF，直到收到 0x10。
  - `0x10`：`st != 7` → 特效从头播，`vtbl+0x4C()` 立即施加一次，`st = 7`，`active = 1000`，`timer = 4000`。
  - 之后走基类事件（LifeTime −1，不会被炸掉）。
- 所以：**开局（元素创建）后 4000 ms 第一次激活，之后每 4000 ms 一次，每次 1000 ms**。各端的激活时刻以仲裁方为准，非仲裁方晚一个网络延迟。[证实]
- 绘制 `0x0061AB47`：激活时特效画在 `(col*40+26, row*40+40)`，然后画基类。
- 3×3 判定都用本机玩家的格子 `int(y)/40`、`int(x)/40`，与图腾格差 ≤ 1（`0x0061ADA0`/`0x0061AFE1`/`0x0061B228`，汇编核对：先取 `+0x33C`（y）与 row 比）。

## 5. 移植建议（服务端权威的 Go 引擎）

原版是"各端本地算元素 + 仲裁方定生死/定时"。服务端权威时可以全部在引擎里确定地算：

1. **事件 1（被炸）**：普通爆炸覆盖到的格子，对三层元素各发一次。爆炸石、冰石、雾石无视 LifeTime 一击即碎；坚石减耐久；其余按 LifeTime。被炸的元素进入 500 ms "消失中"，期间仍挡人挡火，之后移除。
2. **爆炸石**：被炸瞬间对 3×3 发事件 1（递归，同一 tick 内完成）；然后 500 ms 内每 tick，3×3 内未处于死亡状态的玩家直接淘汰（走死亡流程、掉道具，不是困泡）。特效 `Totem_Flame.eff` 从 400 ms 处开始播，锚点 `(col*40+26, row*40+40)`。
3. **图腾**：每个图腾从开局起 4000 ms 计时，激活 1000 ms；激活后计时重置为 4000。冰图腾：激活期间每 tick 给 3×3 内玩家速度附加 −3，并记一个 2000 ms 后 +3 的还原项（速度取值下限 2）；如果不想依赖 tick 率，可以等价成"在范围内期间速度强制 2，最后一次在范围内后 2000 ms 内逐步还原"，但严格复刻应按 tick 记项。火图腾：激活瞬间 3×3 发事件 1，激活期间 3×3 内玩家淘汰。雷图腾：激活期间 3×3 内玩家停下、不能移动/用道具/放泡，按项 2000 ms 还原（禁泡在首项到期时清零）。
4. **激励光环**：开局冷却 20000 ms。玩家在移动、没换格、朝向的相邻格是光环（被挡住）时触发；冷却 <0 才生效。效果给触发者速度/泡数/威力附加值各 +8（取值时截到上限），15000 ms 后各 −8；冷却重置 20000，特效 3000 ms。同一时刻多人顶光环时，原版以仲裁方先处理到的那一个为准。
5. 需要通知客户端的东西：图腾激活时刻（客户端播特效、做 3×3 表现）、光环生效（谁、何时）、坚石的耐久贴图变化、元素消失。原版协议的 0x1176 格式见 §2.3，可以照用 type 9/0x10。
6. 冰石的减速是移动状态（替换减速胶等），冰图腾和光环改的是附加值（可叠加），两者别混用。

## 6. 未知 / 待查

- 属性对象 `+0x0C` 是否就是 `LifeTime`（读取 `mapElem.prop` 的代码没追）——行为与之吻合，标推断。
- `A+0x3B7 == 4` 在规则 1 里的确切含义（推断为垂死/已死）；仲裁方重复发 0xFA7 时接收方是否去重。
- 冰石 5 号移动状态 `+0xC` 返回 0 的含义（可能是"不能主动停下"之类）。
- 玩家 `vtbl+0x88/+0x8C/+0x90/+0x94` 对玩家（不是 NPC）的确切作用，只按 NPC 的同名槽推断。
- 同一帧多个泡炸到同一个坚石，是算一次还是多次（取决于爆炸处理 `0x005F95BB` 一帧内是否合并格子）。
- 元素和图腾的更新是否在开场倒计时（3000 ms）期间就开始走，决定第一次激活/冷却结束的确切时刻。
- `Stone_Ice.eff`、`Stone_Fog.eff`、`Halo_Excite.eff`、`Halo_Compete.eff` 在本发布包里缺失，原版是否另有下载渠道。
