# 探险（规则 12）战斗规则：Client.exe 静态逆向

范围：探险模式（地图原生规则 12）的规则对象、玩家血量、泡泡和接触伤害、NPC 死亡与掉落、分区（BattleField）、过关门、镜头。
PVE NPC 的 AI 只记入口（§8），不展开。流程、服务端和消息清单见 `adventure.md`；竞技 Boss 的受伤和死亡见 `boss-lifecycle-re.md`；泡泡和爆炸见 `bubble-2x2-re.md`。

只做静态分析，没有运行原程序。地址都是 Client.exe 的虚拟地址。

**标注**
- **[证实]**：伪 C 和 capstone 反汇编都核对过。
- **[伪C]**：只读了 Ghidra 伪 C。
- **[手追]**：`0x874000` 以上的变形代码（花指令，`call/pop` 算跳转目标，`lea reg,[reg±imm]` 拼常数），用 capstone 一条条手工跟出来的。只跟了文中写出的那几步。
- **[推断]**：有依据，但没有完全追到。
- **[未知]**：没查清。

**对象记号**（沿用 `boss-lifecycle-re.md`）
- **S**：场景对象。`S+0x4ea4` 是规则对象（`+8` 为规则号）。`S+0x4b34 == S+0x4b40` 表示本机是仲裁方。`S+0x4b38` 是本机玩家角色，`S+0x4b48` 是消息时间戳。
- **M** = `S+0x1310`：角色管理器。
  - `M+0x1338` 是全部角色（数据在 `+0x133c/+0x1340`），即 `S+0x2648`。
  - `M+0x1348` 是 NPC 列表，即 `S+0x2658`。
  - `M+0x3838` 是游戏时间（ms）。
  - `M+0x3b80` 是战场管理器 **BF**（`CBattleFieldMgr`），即 `S+0x4e90`。
  - `M+0x3b84/+0x3b86` 是过关门所在的行、列，即 `S+0x4e94/+0x4e96`。
- **A**：角色。`+0x328` 是运行时 ID，`+0x338/+0x33c` 是像素坐标 x、y（float），`+0x36c` 是状态机，`+0x3b7` 是模式字节，`+0x318` 是免伤组件，`+0x400` 是属性对象 **P**（HP 存在 `P+0xe0`，与 0x1234 异或保存）。
- **格子**：`col = int(x)/40`，`row = int(y)/40`。格心坐标是 `(col*40+20, row*40+20)`。

## 0. 结论摘要

1. **规则 12 的规则对象**：构造函数 `0x00608F40`，虚表 `0x007A429C`，覆盖 18 个槽中的 10 个（§1）。
   - 玩家改用 PVE 玩家类（`0x764` 字节，虚表 `0x007A1E60`，构造时带入勇气值）。
   - **不复活**：槽 4 返回 0。
   - **回合时长 = GAME_BEGIN 的 GameTime × 1000**：客户端把这个字段当作**秒**。服务端现在发 600000，客户端会算成 6 亿毫秒，见 §10-1。
   - 死亡掉落只有 NPC 才有，只掉 `P+0x2c8` 列表里指定 ID 段的物品。
   - 组件表比规则 1 少 2 个、多 5 个：分区锁、NPC 生成器（0x138C）、视野仇恨、**NPC 接触伤害**、**过关门**。
2. **0x10F4 在规则 12 里携带"受伤后的 HP"，不是"扣掉的 HP"**（§3.1）。三个发送方都填 `max(0, HP − 伤害)`；接收方 `0x00601FEC` 只在新 HP 比当前低时，调用角色虚表 `+0x58(新HP)`。规则 1 抓包里那个字段名 LossHP 在规则 12 里不成立。
3. **泡泡伤害**（§3.2）：
   - 伤害等于玩家属性 `PVEBombPower`（PVE 属性对象 `+0x2f0`，即 pvedata 的 `bombpow`），放泡时写进泡对象 `+0x20`，再传给火焰 `+0x24`。
   - 同一格的火焰伤害相加。
   - 打 NPC 时：**实伤 = max(0, Σ火焰 − NPC 防御 `+0x938`)**，防御来自 NPCInfo 的 Defense。
   - 打玩家时：**实伤 = Σ火焰**，没有防御。代码里**不按泡的主人过滤**，所以自己的泡、队友的泡都能伤到玩家。
   - 规则 12 **不会把人炸进泡里**（不发 0xFA5），也**没有受击时的部分掉落**（0x116B）。
4. **NPC 接触伤害**（§3.3）：
   - 组件 `0x00615E6D` 在本机玩家处于站立或行走状态、并且和某个 NPC **在同一格**时，发 0x10F4，新 HP = `max(0, HP − NPC.Harm)`。
   - Harm 存在 `+0x8e8`，即 NPCInfo 的 Harm；道具效果 `TouchHarmValue` 也加在这里。
   - 由受伤者自己的客户端判定。
5. **受伤后**（§2.3，[手追]）：PVE 玩家的 `+0x58` 是 `0x00874E60`。
   - 设 HP；HP 大于 0 时，开 **3000 ms 免伤**（`effect/flash2.eff`，与规则 1 相同）。
   - HP 等于 0 时，进入"垂死"：`+0x3b7=4`，播 cry 动作（8），`+0x3c0=3000`。
   - **没有困泡和救人阶段**：仲裁方的 `CQQTPlayerDieChecker`（`0x0060DE79`）在 `HP≤0 且状态不是 7、12` 时，立即为该玩家发 0xFA7。**玩家死亡也是仲裁方代发**，不是玩家自己发。
6. **NPC 死亡**（§4）：
   - 同一个检查器在 NPC HP 小于 1 时发 0xFA7。**发给服务端的 TCP 包用 `vtbl+0x3c` = `+0x32a` 基础 ID**（XML 的 NPCID，例如 30033）；组播和本机分发的包用**运行时 ID** `+0x328`。
   - 掉落物落在死亡格周围 5×5 的随机空格里。
   - NPC 移出列表时，如果 NPC 全灭、当前分区也没有未生成的 NPC，就**进入下一个分区**（日志 "Enter Next Battle"）。
7. **分区 BattleFields**（§5）：每关有 1～6 个矩形分区 `Field{ox,oy,w,h}`（`ox` 是列，`oy` 是行）。
   - NPC 按分区分批生成：仲裁方在 NPC 列表为空时，生成出生格在当前分区内的 NPC，用 0x138C 广播。
   - 玩家一旦站进当前分区，就不能走出去，碰到边界会闪一层 flame255。
   - 当前分区清空后切到下一个分区；全部分区都完成后，分区变成整张地图。
8. **过关门**（§6）：条件是"NPC 全部生成过 + NPC 列表为空"**第一次成立之后满 10000 ms**，本机玩家所在格等于 `(LevelRow, LevelCol)`，每关只发一次 0x1178。
   - 门**没有专门的绘制代码**。门格上是地图第 2 层自带的箭头地砖（17134/17135/17136 等，可通行，5 帧动画）。
   - `TransDoor*.eff` 属于 `CMETransDoor`，那是关内传送门地图元素（0x1176），与过关门无关。
9. **镜头**（§7，[证实]）：规则 12 的视口是 800×520。
   - 横向死区是镜头左边 200～600 px，纵向是镜头上边 130～390 px。
   - 镜头限制在 `[0, 地图宽−800] × [0, 地图高−520]`，跟随 `S+0x4b38`（本机玩家）。
   - 规则 12 不画竞技的 gametop、gameleft 边框。
10. **PVE 泡泡回复**（§2.2，[证实]）：pvedata 的 `resspeed` 就是 `BombResumeSpeed`（秒，float，`P+0x304`）。
    - 距上次放泡或上次回复超过 `resspeed×1000` ms，就回复 1 个泡。
    - 爆炸时照常再还 1 个。

## 1. 规则对象：规则 12 与规则 1 的差别

规则工厂是 `0x005F47A9`。规则 12 的构造函数 `0x00608F40` 先调用基类 `0x005F49A8`，再令 `+0x14 = 0`，然后换上虚表 `0x007A429C`。[证实]

|---|---|---|---|
| 0 `+0x00` | `0x005F49BA` | `0x00608F5C` | 析构 |
| 1 `+0x04` | `0x005F49DD`：`0x005B653F` 放人；设 `+0xc/+0x10 = S+0x4e88/0x4e8c` | **`0x00608F83`**：`+0x14 = GameBegin[+0x5aa]*1000`；`0x005B6E07` 放人（建 PVE 玩家）；然后 `0x005B63CD`、`0x005B6441` | 开局放人（§1.1） |

| 4 `+0x10` | `0x005F4A5D` 返回 0 | `0x006094CD` 返回 0 | **是否定时复活**。0xFA7 接收 `0x00606606` 和复活组件 `0x00615AAE` 都先问这一槽 |
| 5 `+0x14` | `0x005F4A60`：3600000，或者在 app`+0x56f04` 为真时返回 600 | `0x006094D0` 返回 **3600000** | 复活延迟（只在槽 4 为真时使用） |

### 1.1 放人 `0x005B6E07`（规则 12）[伪C]

和规则 1 的 `0x005B653F` 只有一处不同：建角色用的是 `0x005CB310`。它 `new 0x764`，调用 `0x005B985C(M, PlayerID, Role, Team, Points)` 构造 PVE 玩家（虚表 `0x007A1E60`，`+0x3a4` = 勇气值），再调初始化 `0x0088338C`（变形代码，**读不到属性是怎么写进去的**）。

```
table = 0x005C18E2(M)          // 出生点表：先 A、B 交替，再放剩下的 A，最后剩下的 B；每项 (row, col)
if len(table) < 玩家数: 报错，返回失败
for i, p in GAME_BEGIN.players:          // 每个玩家 0x49 字节：+0x13 PlayerID，+0x15 Role，+0x16 Team，+0x1b Points
    a = new PVEPlayer(p.id, p.role, p.team, p.points)
    a.setCell(table[i].row, table[i].col);  a.pos = (col*40+20, row*40+20)
    0x005B9642(p.items...)                  // 准备道具
M+0x396c = 人数
```

PVE 地图都只有 4 个 A 组出生点、0 个 B 组，所以第 i 个玩家站在 A[i]，按 GAME_BEGIN 的顺序。

## 2. 玩家：属性、血量、泡泡、死亡

### 2.1 属性对象和 pvedata [证实偏移，pvedata 对应为推断]

PVE 玩家的 `+0x400` 是 PVE 属性对象，虚表 `0x007A1B7C`，构造函数 `0x005AAA7B`。和普通属性对象 `0x007A1B40` 不同的槽：

| 槽 | 实现 | 含义 |
|---|---|---|
| `+0x0c` 设 HP | `0x005AAC41` | `HP = min(v, MaxHP)`，与 0x1234 异或后存到 `+0xe0` |
| `+0x10` 加 HP | `0x005AAC9E` | 加后不超过 MaxHP |
| `+0x14` 减 HP | `0x005AAD4E` | |
| `+0x18` MaxHP | `0x005AAC3A` | 返回 `+0x2fc` |
| `+0x24` 泡泡伤害 | `0x005AAABD` | 返回 **`+0x2f0`（PVEBombPower）**。普通属性对象的这一槽返回 0 |
| `+0x28` 加泡泡伤害 | `0x005AAAC4` | `+0x2f0 += v`，道具效果 `PVEBombPower` 调用它 |
| `+0x2c` 可用泡数 | `0x005AAB3B` | 上限 = 基础 `+4` + 道具 `+0x90` + 拾取数，不超过 `+0x18`；可用 = 上限 − 已用 `+0x27c` |
| （字段） | `+0x304` | **BombResumeSpeed**（float，秒，加密保存）。道具效果 `BombResumeSpeed` 在 `0x005FB041` 里减去 `v×0.01` |

PVE 玩家的初始化 `0x0088338C` 在变形代码里。按名字推断，pvedata 的字段对应为：

| pvedata 字段 | 去向 |
|---|---|
| `hp` | HP 和 MaxHP（`+0xe0`、`+0x2fc`） |
| `bombpow` | `+0x2f0`，就是 PVEBombPower，也就是伤害 |
| `resspeed` | `+0x304` |
| `bombnum` | 基础泡数 |
| `speed` | 速度档 |

`GetPVEData`（`0x0054CD50`）返回的 `tagPVEDATA` 是 6 个 dword：`m_unLevel, m_unHp, m_unBombNum, m_fBombReSpeed, m_unBombPow, m_unSpeed`，由 room 模块虚表 `+0x310` 填写（QQTSection.dll 里同样是变形代码）。**泡的臂长**仍然用 `P.vtbl+0x20`，和伤害无关。

### 2.2 泡泡回复（`resspeed`）[证实]

PVE 玩家每帧调用 `vtbl+0x30` = `0x005B9F1C`：

```
base_update(dt)
limit = ftol(P.BombResumeSpeed * 1000.0f)      // 常数 0x797C4C = 1000.0
if A+0x760 > limit:  A+0x760 = 0; P.used(+0x27c) -= 1 (only if used >= 1)   // 0x005AE064(1)
A+0x760 += dt
```

- 放泡走 `vtbl+0x1c` = `0x005BA3CB`：`A+0x760 = 0`，`P.used += 1`。如果是本机玩家，还调用 `ui_SetBaseItemTimeCur(0)` 和 `ui_SetBaseItemTimeSpeed(100/resspeed)`（resspeed 小于 0.5 时原版直接用 0.5 乘 100，得 50；本实现按原版 bug 修正为 200，见 `pve-panel-re.md`）。
- 爆炸时 `0x00606F28` 对泡的主人照常调用 `0x005AE052(1)`，又还一个泡。规则 12 不例外，只有泡类型 9/13/14 和规则 8 不还。
- 结果是：PVE 玩家场上的泡可以多于上限。lev_0 每 2 s 回复一个，lev_15 以上每 0.8 s 一个。

### 2.3 受伤 [证实接收方；PVE 玩家的 +0x58 为手追]

0x10F4 的接收方 `0x00601FEC` 在规则 12 下的流程（反汇编在 `0x006020D9`～`0x0060211F`）：

```
a = find(ObjectID)
if !a: return
if rule != 12 && !0x005AD175(a): return     // 规则 12 不检查"可受伤"
if !msg.IsAvatar && a+0x404: 0x005ADF5A(0)  // 解除变身
loss = P.HP - msg[+0xb]                     // msg[+0xb] 是受伤后的 HP（u16）
if loss < 1: return                         // 新 HP 不比当前低，忽略
a.vtbl+0x50(loss)                           // 只是调试："HP:%d" 头顶文字显示 900 ms（0x005AC606）
log("Player %d be Harmed... HP Loss = %d", msg[+0xb])
a.vtbl+0x58(msg[+0xb])                      // 规则 12 的受伤处理，参数是新 HP
// 规则 12 后面没有 0x116B 和 0xFA7 分支，那两段只认规则 1/2、7/8
```

普通玩家类的 `+0x58` 是空函数 `0x005AB14D`，所以规则 12 必须使用 PVE 玩家类。

PVE 玩家的 `+0x58` = `0x00874E60`，手追结果：

```
log("Player Uin = %u be Harmed, HP Loss = %u", A+0x37c, newHP)
A+0x478 = 1; A+0x3b7 = 1
this->vtbl+0x0c(newHP)        // 0x0088B534（变形代码）：设 HP；推断同时调用 ui_UpdatePVEPlayerLife
if P.HP > 0:                  // 0x005E9C67 → 0x0088B26B
    0x005B514E(x, y); 0x005B4EFD()      // 闪光特效定位
    0x005B5202(3000)                    // ebp = 0xC91EC4F0 + 0x36E146C8 = 0xBB8；3 s 免伤（flash2.eff）
else:
    0x00881826()                        // 0x005ACD09 的变形副本："垂死"
```

`0x005ACD09` 是 `0x00881826` 的普通代码版本，也是状态 7 的进入函数（`0x005C0E7D`）。手追核对过的部分：

```
清掉变身 +0x404
+0x3b5 = 0xFF; +0x3b7 = 4; +0x3b8 = 1; +0x478 = 1
if 是 NPC:  +0x3c0 = 400;  avatar 播动作 6（actDie），播一次，朝 270°   // 0x005B5013
else:       +0x3c0 = 3000; avatar 播动作 8（actCry），循环，朝 270°      // 0x005B4FBB
P.0x005AA040(1)
```

`+0x3c0` 由 `0x005AEA07` 每帧减去 dt。小于 0 之后不再画属性条之类的东西（`0x005AF118`）。

**受伤后的免伤**：免伤期间 `0x005AD175` 为假。爆炸判定（`0x00607899`、`0x00607DDC`）和持续火焰判定（`0x0060C63A`）都要求它为真，接触伤害（`0x00615E6D`）要求 `+0x318` 未激活。所以**同一个玩家每 3 s 最多受一次伤**。

### 2.4 HP 归零 → 死亡（**没有困泡，也不能被救**）

- 仲裁方组件 `0x0060DE79` 遍历 `M+0x133c` 里的全部角色，`vtbl+0x5c` 为真就发 0xFA7。
  - PVE 玩家的 `+0x5c` = `0x00889510`，手追：`HP>0 → 假`；否则读状态 `0x005C0BDA`，**等于 7 或 0xC 时为假，其余为真**。
  - PVE NPC 的 `+0x5c` = `0x005BC922`：`HP<1 且状态≠7`。[证实]
- 所以 HP 一归零，仲裁方下一帧就发出死亡。0xFA7 的接收方（`0x00606606`）把状态切到 7（`0x005C0964`，再走一次 `0x005ACD09`），并把 HP 置 0。
- 规则槽 4 返回 0，所以**不建复活计时器**。
- 状态 7 的时长是 3600000 ms（`0x005C0E8E`）。PVE 玩家的绘制函数 `0x005B9FA1` 在状态 7 持续超过 3599999 ms 之前，一直画垂死或尸体姿势。
- 规则 12 的玩家**不会**被泡泡困住，因为 `0x00607A23` 在规则 12 下不发 0xFA5，所以队友的"接触救人"（`0x0060C148`，要求状态 5）在正常战斗中不会发生。只有陷阱类场景对象或道具效果 `BeExplode`（`0x005B52D4`）还能把人困住。
- 0xFA7 的组成（`0x0060DE79`）：`{u16 id, u32 Time=M+0x3838, u16 X, u16 Y, u8 n, n×{u32 item, u8 row, u8 col}}`。玩家死亡时 `n = 0`，规则 12 的槽 6 只处理 NPC。
  - 先 `0x005A1DE1(0xFA7)` + `0x00886494`（TCP 发给服务端）。
  - 再组播 `0x005A2F4C`，并本机分发 `0x005C8794`。
- **更正 `adventure.md` §1.4**：规则 12 的玩家死亡**由仲裁方的检查器代发**，不是玩家自己发。

### 2.5 复活（0x0FBA）

- 规则 12 **没有定时复活**：槽 4 返回 0，`0x00615AAE` 和 `0x00606606` 都在这一步退出。[证实]
- 能复活的途径都是道具效果（准备道具）。属性名表在 `0x005FA37A`：
  - `Relive`：`0x005C0B08`（切到复活状态 8）。如果这个角色是本机（`M+0x3824 == M+0x3830`），**只通过 TCP 发 0xFBA 给服务端**（没有组播）。字段是 `{u16 id, u32 time, u8 y/40, u8 x/40}`。
  - `0x005B5644`（要求状态 7 或 8）：规则 12 下复活格取**当前位置**（`y/40, x/40`），其他规则取出生格 `+0x470/+0x472`。它发 TCP、组播、本机分发三路。调用方在变形代码里 [推断：复活类道具]。
- 复活状态 `0x00881FE5` 的效果已经用 Unicorn 查过：`+0x3b7 = 1`，3000 ms 免伤（`other-rules.md`）。
- 其他与血量相关的效果：`HP`（v<1 时走 `0x005B57DB`，自己给自己发 0x10F4，新 HP = HP − |v|；v≥1 时调用 `vtbl+0x40` 加血）、`SetCurPercentHP`、`SetTotalPercentHP`、`Invincible`、`Saved`（目标的 `+0x3b7` 必须是 3，发 0xFAB）。

## 3. 伤害

### 3.1 0x10F4 在规则 12 里的语义 [证实]

线上格式不变：`u16 ObjectID, u32 Time, u16 PosX, u16 PosY, u8 IsAvatar, u16 V`，共 13 字节。规则 12 的三个发送方都令 **V = max(0, 受伤者当前 HP − 实伤)**，接收方的处理见 §2.3。实伤为 0 时：

- 爆炸判定直接不发（`if dmg==0 && rule==12: skip`）；
- NPC 防御抵消了全部伤害时，V = HP，接收方算出 loss = 0，也会忽略。

发送方：

| 发送方 | 触发 | 实伤 |
|---|---|---|
| `0x00607A23`（由 `0x00607899` 判本机玩家、`0x00607DDC` 在仲裁方判每个 NPC） | 收到 0xFA4 爆炸、火焰生成之后各判一次 | Σ火焰 `+0x24`；受伤者是 NPC 时再减防御 |
| `0x0060C63A`（组件，每帧） | 5 个采样点里至少 4 个落在有火焰的格子里，并且可受伤 | 同上 |
| `0x00615E6D`（组件，每帧） | 本机玩家和 NPC 在同一格 | NPC.Harm |
| `0x005B57DB` | 道具效果 `HP<0` | \|v\| |

三路发送：TCP（`0x005A1DE1`）、组播（`0x005A2F4C`）、本机分发（`0x005C8794`）。

### 3.2 泡泡和火焰 [证实]

```
// 放泡（本机 0x00610BA0，远端 0xFA3 的接收方 0x0060857C）
bomb+0x1e = owner.P.vtbl+0x20()      // 臂长
bomb+0x20 = owner.P.vtbl+0x24()      // PVE：PVEBombPower（+0x2f0）；普通属性对象为 0

if rule != 12: 0x005D3E64(row,col)   // 移除火焰格里的其他泡（规则 12 不做，推断交给各自的 0xFA4 处理）

// 判定（0x00607A23，规则 12 分支，反汇编在 0x00607B9C～0x00607BF7）

    d = target.vtbl+0x48() - dmg           // PVE NPC：+0x938 防御
    V = max(0, HP + min(0, d))             // 也就是 HP - max(0, dmg - 防御)

```

- 防御 `+0x938` 由道具效果 `Defense`/`Defence` 通过 `vtbl+0x80`（`0x005BA692`）累加。初值推断来自 PVENPC 的 Defense（偏移 `+0x28`），NPC 初始化 `0x00891752` 是变形代码 [推断]。
- **NPC 的泡对玩家造成多少伤害**取决于 NPC 属性对象的 `vtbl+0x24`。NPC 属性对象在变形代码里创建，属于哪个类、`+0x2f0` 填什么，都 [未知]。按命名推断是 Harm，或者是另一个值；实现时先用 Harm，等抓包核对。
- 判定没有队伍或主人过滤：**玩家会被自己和队友的泡炸伤**，NPC 也会被 NPC 的泡炸伤 [代码中未见过滤]。

### 4.1 死亡 0xFA7 [证实]

由 `0x0060DE79` 发出，只在仲裁方执行：

```

    msg = {id=npc+0x328, M+0x3838, x, y, items...}
    items = rule.slot6(npc)  (§4.2)

- PVE NPC 的构造函数 `0x005BA4F2(M, entry.NPCID, entry.ImageID(+0x20), team=9)` 先把 `+0x328` 和 `+0x32a` 都设成 `entry+0`。

- 因此推断：**0x138C 的 PVENPC.NPCID 是读关卡时分配的唯一运行时 ID，NPCBaseID 才是 XML 里的 NPCID**；初始化（变形代码）把 `+0x32a` 改成 NPCBaseID。服务端要求 0xFA7 带基础类型（`adventure.md`），与抓包中的 30033 一致。[推断]
- 运行时 ID 应放在 30000～30200 之间：0x116B 的接收方和 0xFA7 的接收方都按这个区间认 NPC。
- 0xFA7 的接收方 `0x00606606` 对 NPC 的处理：播 `x35_01.wav`，道具以 400 px/s 飞出，`0x005AE19A(1)` 死亡特效，`0x005DAC00`，`0x005B8ECC` 移除并析构，然后检查是否进入下一个分区（§5.1）。规则 12 不调用 `0x005B9390/0x005B9500`。

## 5. 分区（BattleFields）和 NPC 分批生成

### 5.1 CBattleFieldMgr 的布局 [证实偏移；XML 字段对应为推断]

| 偏移 | 含义 |
|---|---|
| `+0x04` | 当前分区序号 |
| `+0x0c` | `vector<Field{ox,oy,w,h}>`，每项 16 字节 |
| `+0x20..+0x2c` | **当前分区矩形** `{ox(列), oy(行), w, h}`（`0x005E7F92` 取出） |
| `+0x44` | `vector<PVENPC>`，每项 0x48 字节：`+0x3c` BornRow，`+0x40` BornCol，`+0x28` Defense…… |
| `+0x54` | `vector<int>` 每个 NPC 的"已生成"标志 |
| `+0x64` | 每个 NPC 的技能表（16 字节，内含 `vector<0x38 字节>`） |
| `+0x84/+0x88` | ContinueID / NextMapIndex（0x1178 用到） |
| `+0x8c/+0x90` | 过关门的行、列 → `M+0x3b84/+0x3b86`（`0x005E7320`）。`M+0x3b86` 的默认值是 0x27 = 39（`0x005B5B4C`） |
| `+0xa4` | 分区锁定标志 |

函数：

- `0x005E80B9`：取出**未生成、出生格落在当前分区内**的 NPC。边界**包含右下**：`oy ≤ row ≤ oy+h`，`ox ≤ col ≤ ox+w`。
- `0x005E818F`：收到 0x138C 后，把对应 NPC 标记为已生成。
- `0x005E823C`：`Σ标志 ≥ 总数`，即**全部 NPC 都生成过**。
- `0x005E8279`：当前分区里还有没生成的 NPC 时返回 0。这里的边界**不含右下**：`< ox+w`。
- `0x005E801B`：进入下一个分区，`idx += 1`，`+0xa4 = 0`，矩形换成下一个分区；已经是最后一个分区时，`+0xa4 = 1`，矩形 = `{0,0,地图列数,地图行数}`。
- `0x005B8ECC`（移除 NPC）：规则 12 下，NPC 列表变空并且 `0x005E8279` 返回 1 时，记日志 "Enter Next Battle"，调用 `0x005E801B`。

### 5.2 生成 NPC：`0x006162F6`（CQQTPVENPCProduceChecker）[证实]

```
仅仲裁方；check(actor) 中 actor 不是 NPC（即本机玩家那一次调用）
if NPC 列表为空:
    list = BF.produce()                          // §5.1 的 0x005E80B9
    if list 非空:
        msg = {u32 n, n × PVENPC(72 字节，原样 memcpy)}
        本机分发 + TCP + 组播 (0x138C, msg)
```

- 开局约 3 s 后（组件开始运行），生成第一个分区的 NPC。
- 当前分区清空后，`0x005B8ECC` 切换分区，下一帧生成下一个分区的 NPC。**不用等玩家走进去**。
- 0x138C 的接收方 `0x005FCFD3`，对每个条目：
  1. 建 NPC：`0x005CB43C`，`new 0x948`，构造函数 `0x005BA4F2`，然后 `vtbl+0xdc(entry)`；
  2. 设出生格和坐标 `(BornCol*40+20, BornRow*40+20)`；
  3. 解除变身；
  4. 挂技能表：`0x005E7F35` → `0x005E974F`；
  5. 加入 NPC 列表：`0x005FCE22`；
  6. 加 HUD 行：`0x005DAB31`。

  全部处理完后调用 `ui_InitPVEBoss()`。
- 0x138C 的线上格式是 `u32 count + count × 72 字节`，与 `adventure.md` 列出的元数据顺序一致（`+0x00` NPCID，`+0x04` NPCBaseID，`+0x08` IsBoss，`+0x0c` NickName[20]，`+0x20` ImageID，`+0x24` MoveStrategy，`+0x28` Defense，`+0x2c` HP，`+0x30` Speed，`+0x34` Harm，`+0x38` BattleStrategy，`+0x3c` BornRow，`+0x40` BornCol，`+0x44` View）。网络层是否原样紧排，由 `0x005A1DE1` 的序列化决定 [推断]。

### 5.3 走进分区就锁住 [证实]

- `0x0061667E`（本机玩家）：`BF+0xa4 == 0`，并且本机玩家所在格在当前分区内（`(col-ox)&0xFFFF < w`、`(row-oy)&0xFFFF < h`）时：
  - `BF+0xa4 = 1`；
  - 在分区的**每一格**放一个 flame 场景对象，id 0xFF（`object/flame/flame255_stand.img`，3 帧，40×40），`+0x24 = 0`，即不造成伤害，作为闪烁提示。
- 移动限制 `0x005B7C16(row, col)`：只在规则 12 且 BF 存在时生效；其他规则的矩形是 `{0,0,15,13}`。

  ```
  if 目标格越出地图: 0
  if 本机玩家当前在分区内: return 目标格在分区内
  else: return 1          // 在分区外可以自由走，例如切换分区之后、走进新分区之前
  ```

- 碰到分区边界时闪一次（`0x005F3810`，本机移动，在 `0x005F38F9` 一带）：
  - 条件：规则 12，`BF+0xa4` 为真，这一帧被挡住没走动，并且正面朝着分区边界（朝上且 row==oy、朝下且 row==oy+h-1、朝左且 col==ox、朝右且 col==ox+w-1）；
  - 如果所在格里还没有 flame255，就把整个分区重新铺一遍 flame255。
- 之后 `+0xa4` 只在进入下一个分区时清零。

## 6. 过关门 `0x00615CAC` [证实]

组件构造时 `+0x08 = 10000000`，`+0x0c = 0`。

```
check(actor):
  if isNPC(actor): return
  if NPC 列表非空: return
  if !BF.allProduced() || this.sent: return      // 0x005E823C
  now = M+0x3838
  if this.t0 > now: this.t0 = now; return        // 第一次满足条件时开始计时
  if now - this.t0 < 10000: return               // 0x2710
  if (int(actor.y)/40, int(actor.x)/40) == (M+0x3b84, M+0x3b86):   // 行比较 LevelRow，列比较 LevelCol
      this.sent = 1
      TCP(0x1178, {u16 actor.id, u32 now, u32 BF+0x84 ContinueID, u32 BF+0x88 NextMapIndex})
```

- **只经 TCP 发给服务端**（`0x00886494`），不组播。actor 实际上是本机玩家（§1.2）。
- 10 s 从"所有分区的 NPC 都生成过并且全部死亡"**第一次被检测到**的时刻算起。最后一个 NPC 死亡之后，下一帧就会检测到。
- 最后一关的 XML 里 `NextMapIndex=""`，门是 `(0,0)` 或空。客户端照样会在玩家站上 (0,0) 时发 0x1178。服务端的规则是"最后一关清怪后 10 s 自动判胜，提前进门直接判胜"（`adventure.md` §1.5）。
- **门的外观**：
  - 普通代码里没有绘制函数读 `M+0x3b84/0x3b86`。
  - 用 `client/native/qqtclient/battle/mapfile.py` 核对了前 21 关的门格：第 2 层都是地图自带的可通行地砖（GridAttr 3855），例如 1601～1603 是 17136（`common/elem136`，向右的箭头，41×43，5 帧），1604 是 17134（向上），1605 是 17135（向下），1607～1614 是 12006/12007，1616～1621 是 17045。
  - 结论 [推断]：**门始终画在地图上，不随清怪出现**，只是在门的条件满足之前踩上去不会触发。
- `effect/TransDoor{,_Enter,_Trans}.eff` 属于 `CMETransDoor`（注册在 `0x00613C20`，事件处理在 `0x00613E4D`）。它是关内**传送门**地图元素：踩上去发 0x1176，2000 ms 后传送，与过关门无关。

  else:                  if W-800 < max(camX,0): camX = W-800
                         elif camX <= 0: camX = 0
  // 纵向，死区 [camY+130, camY+390]
  if py < camY+130:      camY = (py < 130) ? 0 : py-130
  elif py > camY+390:    camY = (py > H-130) ? H-520 : max(0, py-390)
  else:                  if H-520 < max(camY,0): camY = H-520
                         elif camY <= 0: camY = 0
  view = 800×520
app+0x56fec..0x56ff8 = {camX, camY, viewW, 520}; M+0x3b68/+0x3b6c = cam; 特效层的滚动量 0x8037B0/B4 = cam (0x00584260)
```

- 精灵定位 `0x005C477E`：`屏幕 = 世界 − 锚点 − cam + (−12, +1)`。所以 PVE 和竞技使用**同一套**世界坐标到屏幕坐标的换算，只是多减了镜头位置。
- 地图格只画可见范围：`0x005B81FE` 画 `[cam/40 − 1, (cam+view)/40 + 1)`。
- 规则 12 不画竞技的边框图（`M+0x3b88/8c/90`，即 gametop、gameleft，见 `0x005B82C8`）。
- 屏幕上的位置 [推断]：竞技场地的原点在 (10,27)（`scene.py` 的 `FIELD_ORIGIN`），所以 PVE 的视口大约是屏幕 x 10～810（最右 10 px 在屏幕外）、y 27～547。上面再叠 PVE 界面：顶部 Boss 血条、左侧 `pvePlayerList`、右下 `pveFuncDlg`。需要截图核对。
- 所有 PVE 地图都至少 20 列（W ≥ 800）、13 行（H ≥ 520），所以 W−800 和 H−520 不会为负。

## 8. PVE NPC（AI 的入口，本文不展开）

- 类：`0x948` 字节，虚表 `0x007A1F54`，构造函数 `0x005BA4F2`（TeamID 固定为 9），初始化 `vtbl+0xdc` → `0x00891752`（变形代码）。
- 字段：

  | 偏移 | 含义 |
  |---|---|
  | `+0x8e8` | Harm（`+0xd8` 读，`+0xbc` 加） |
  | `+0x938` | Defense（`+0x48` 读，`+0x80` 加） |
  | `+0x944` | IsBoss（`+0x4c`，`GetPVEBossInfo` 用） |
  | `+0x8a0` | MoveStrategy |
  | `+0x8a8` | 是否在战斗状态（`+0xb4`） |
  | `+0x8b0` | NPCBounds（`+0xb8`） |
  | `+0x8c0` | View |
  | `+0x8f4` | 战斗持续时间 |
  | `+0x930/+0x934` | 一个倒计时 |

- 移动决策 `vtbl+0x70` = `0x005BAE70`：
  - 先 `0x005BADE5` 切换"战斗/归位"状态（日志 "NPC STATE CHANGE TO NPC_BATTLE"；进入战斗时把 MoveStrategy 暂时换成 4，结束后恢复）；
  - 再按 MoveStrategy 1～5 分派到 `0x005BAEF1`、`0x005BB069`、`0x005BB1E1`、`0x005BB33A`、`0x005BB510`。
- 视野判定 `vtbl+0xc4` = `0x005BAD0C`：横向、纵向的格数都不超过 View。仇恨相关是 `+0xc8`、`+0xcc`（变形代码）、`+0xd4`。

## 9. 移植清单（Go 引擎 / sidecar）

1. **规则 12 的开关**：
   - 单队合作；
   - 地图不限 15×13；
   - 回合时长 = GameTime×1000（§10-1）；
   - 不定时复活；
   - 出生按 A 组顺序。
2. **血量模型**：
   - 玩家属性从 pvedata 按勇气值取：`hp`、`bombpow`（伤害）、`resspeed`、`bombnum`、`speed`；
   - NPC 属性来自 XML：`HP`、`Defense`、`Harm`。
3. **伤害**（每个受伤者每 3 s 最多一次）：
   - 泡泡：`实伤 = Σ同格火焰的主人 bombpow`；NPC 再减 Defense，不低于 0；不分敌我。
   - 0xFA4 时判一次，之后站在火里每帧再判（4/5 采样点）。
   - NPC 和玩家同格时，玩家受 Harm 点伤害（只判本机玩家，状态为站立或行走）。
   - 发 0x10F4 时 V = 受伤后的 HP。
4. **HP 归零**：先进入垂死（玩家 cry 动作，`+0x3c0=3000`；NPC die 动作，400），仲裁方随即发 0xFA7。服务端收到基础 ID，同伴收到运行时 ID。
5. **NPC 死亡掉落**：取 `P+0x2c8` 里指定 ID 段的物品，按数量展开，落在死亡格周围 5×5 的空格里（左上角不越过 NPCBounds 的左上角）。受击时不掉落。
6. **分区**：
   - 开局约 3 s 后，生成第一个分区里的 NPC（0x138C）；
   - 当前分区清空后切到下一个分区，并立即生成；
   - 本机玩家走进当前分区后就出不去，碰到边界闪 flame255；
   - 最后一个分区完成后，分区变成整张地图。
7. **门**：全部生成过且全部死亡，满 10 s 后，本机玩家站在 `(LevelRow, LevelCol)` 时，经 TCP 发一次 0x1178。
8. **泡泡回复**：自上次放泡或上次回复起超过 `resspeed×1000` ms，回复一个泡；爆炸时照常归还。
9. **镜头**：按 §7 实现，视口 800×520。

## 10. 未证实 / 待查

1. **GameTime 的单位**：规则 12 的槽 9 是 `GameBegin[+0x5aa] × 1000`（`0x00608F96 imul eax,eax,0x3E8`），计时显示也用它。服务端的 `DefaultAdventureGameTimeMS = 600000` 会被当成 600000 秒。原版服务端很可能发的是秒（如 600）。需要用原版抓包核对；在确认之前，原生客户端按"秒"解释，服务端最好改成发 600。
2. PVE 玩家和 NPC 的初始化（`0x0088338C`、`0x00891752`）、设 HP（`0x0088B534`、`0x0087AF85`）都是变形代码。pvedata、XML 字段落到哪个偏移，大半是按名字推断的；`ui_UpdatePVEPlayerLife`、`ui_UpdatePVEBossLife` 的调用时机也没追到。可以用 `tools/probe_vm.py` 黑盒运行确认（本次按要求没有运行）。
3. NPC 的泡对玩家造成的伤害（NPC 属性对象的 `vtbl+0x24`），以及 NPC 受伤后是否免伤。
4. 0x138C 里的运行时 NPCID 怎样分配（推断在 30001～30199 里按顺序分配），NPCBaseID 是否就是 XML 的 NPCID。
5. `P+0x2c8` 掉落列表的来源（0x138A 的 `S+0x5c2` 在普通代码里没人读），以及 DropTime 定时掉落、规则 12 下的 0x116B 发送方。
6. 道具 `Relive` 只经 TCP 发 0xFBA，同伴怎样得知：是服务端转发，还是另有组播（`0x005B5644` 的调用方在变形代码里）。

8. 规则 12 下 `0x005D3E64`（移除火焰格里的泡）被跳过的确切含义。
