# DYMASK 动态遮罩

2026-11-03。原版 gameUI.dll 静态反汇编和 Unicorn 黑盒调用，已接入原生渲染器。

## 规则

`0x10011E2A` 构造当前角度、步进和目标角度，均从 0 开始。`0x10011E82` 读取 `curangle`、`stepangle`、`destangle`。`0x10012057` 每帧按 `step × 秒数` 接近目标，达到目标就截断，不继续越过。

`0x100120E7` 在角度小于 0 或大于等于 360 时不画。在范围内按图片帧的矩形生成三角扇裁切；擦除从十二点方向顺时针推进：

| 当前角度 | 可见部分 |
| --- | --- |
| 0 | 全图 |
| 90 | 左半与右下象限 |
| 180 | 左半 |
| 270 | 左上象限 |
| 360 | 不画 |

45/135/225/315 度穿过矩形四角，因此非正方形图片要按归一化图片坐标算射线，不能直接用屏幕像素的圆周角切图。图片自身的透明度、帧偏移和控件透明度继续生效。

## 黑盒证据

`/private/tmp/qqt-mall-re/probe-mask.py` 用既有 Win32Emu 载入原版 gameUI.dll，构造一个 64×64 的假图片描述；截获 GFX 接口 `+0x118` 四边形与 `+0x11C` 三角扇绘制参数。只在模拟器内替换图片查询与绘图接口，数学运算使用 sin/cos/tan 等价计算，固定不影响形状的控件不透明度。原版文件不改写。

在 0、45、90、135、180、225、270、315、359、360 度逐次调用 `0x100120E7`，顶点和贴图坐标证实上表；360 度没有任何绘图调用。该实验只验证几何与方向，没有运行 Windows 图形驱动，像素边界和原版 Direct3D 的半像素采样仍可能相差 1 px。

## 移植与验证

`render.remaining_angle_image` 从源图片副本裁切保留扇区，不污染共享精灵缓存。`UIRuntime.tick` 按度/秒推进 DYMASK，支持两个方向并停在目标值。

三个测试覆盖四个象限/360 度、矩形归一化角度、源图片不被改动、自动推进和反向截断。离线练习把 baseItemCycle 从 0 以 90°/秒推进到 360，分别截取约 45/135/225/315/360 度的界面；见 `/private/tmp/qqt-mall-re/mask-live`，无脚本异常。

本次只补控件。带入道具的槽位排法与冷却触发语义仍需追保护代码，不能因为遮罩能画就认为它们已经完成。
